# parism 사람 실험 (5~8명) — 절차서

계획서 10장의 남은 절반을 실행하기 위한 문서다. 기계 하네스(`experiment-a.mjs`, `experiment-b.mjs`,
`demo-60s.mjs`, `perf-gate.mjs`)는 **기계적으로 채점 가능한 것만** 잰다. 이 절차서는 사람이 매기는
나머지 — LLM 이 문장을 이해했는가, 사람이 확인하는 데 몇 초가 걸렸는가 — 를채집한다.

**여기에는 결과가 없다.** 과제와 채점 규칙만 있다. 수치를 만들기 전까지 어떤 결론도 읽지 말 것.

---

## 0. 이 실험이 답하려는 질문과 답하지 않는 질문

**답하려는 것**

1. 같은 질문에 대해 parism 경로와 기존 경로 중 어느 쪽이 **더 자주 맞았나**.
2. 맞힌 쪽이 **몇 번의 시도**를 거쳤나 (추측은 틀리다, 고쳐야 한다).
3. 사람이 결과를 **몇 초 만에** 신뢰할 수 있었나 (검증 시간).
4. 사람이 **포기하고 원래 도구로 돌아가는** 비율.

**답하지 않는 것** — 이 실험으로 답하려 들면 안 된다

- 토큰 절감률. 같은 문장을 LLM 이 읽으면 토큰이 드는 것이지, 그게 이 실험의 지표가 아니다.
- 사람이 "편안하다"고 느낀 주관적 만족도. 만족도와 정확도는 자주 어긋난다.
- 모델이 "더 똑똑해서" 해결한 것. **같은 모델·같은 버전·같은 온도·같은 프롬프트**로 고정한다. 

지표가 세 개라도, 사람이 매기는 성격의 숫자가 두 개 포함된다(확인 시간, 포기율). 그래서
**기계 채점 항목과 사람 채점 항목을 표에서 분리해 적는다.** 섞으면 어느 쪽이 옳은지 나중에 알 수 없다.

## 1. 참가자 (5~8명)

**모집 기준 — 다음을 모두 만족할 것**

- 셸을 하루에 씁니다. "사용해 본 적 있음"이 아니라 **일상에서 씁니다**.
- 쉘 스크립트를 씁니다(awk/sed 관용구를 아니면 실험 대상이 아닙니다).
- 최근 3개월 안에 터미널 작업 도구(ripgrep fd bat eza 등)를 새로 써 본 적이 **있어도 되고 없어도** 됩니다.
- parism 을 써 본 적이 없어야 합니다. **한 번이라도 읽었다면 참가 불가**(이해 편향).

**인원은 왜 5~8명인가**

이 크기에서는 통계적 유의성 검정을 할 수 없습니다. 그래도 필요한 이유는 두 가지뿐이고,
둘 다 이 5~8명이 충족하는지 볼 수 있는 수준입니다:

1. 참가자 간 차이가 개별 수행 편차를 얼마나 덮는지(범위).
2. **이탈이 없었는지.** 과제 도중에 그만둔 사람이 있으면 그 사람의 시도는 편향을 만듭니다.

다음을 미리 밝힙니다: **이 실험은 유의성 검정이 아닙니다.** 신뢰구간을 붙이되 그것이 유의성은
아니라고 문서에 적습니다. 유의성은 표본을 늘리거나(그리고 그러면 그때도 한계가 있다) 다른
설계(집단 내 반복)로 가야 합니다.

**동일한 개발자군에서 뽑습니다.** 다른 회사의 같은 직급끼리 모으면 아무것도 못 말하는 결과가 나옵니다.

## 2. 고정할 것 (하나라도 흔들리면 결과가 무의미해진다)

| 항목 | 고정 값 | 흔들리면 어떻게 망가지는가 |
|---|---|---|
| 모델 | 참가자 전원 동일 | "parism 이 나았다"가 아니라 "그 모델이 그날 좋았다"가 된다 |
| 모델 버전 | 날짜까지 고정 (예: `2026-10-05`) | 같은 이름의 다른 가중치 |
| 온도 | 0 | 0이 아니면 재현이 안 된다 |
| 프롬프트 | 아래 4장 텍스트를 **글자 그대로** | 실험자가 그때그때 다듬으면 사람이 바뀐다 |
| 타이머 표기 | 초 단위, 소수점 버림 | 일관성 없으면 분석 불가 |

**온도 0이어도 완전 결정론은 아니다.** 그래서 5회 반복을 한다. 1회로 재면
"그 운의 결과"를 측정하는 셈이다.

## 3. 손님 시나리오 (warm-up) — 본 실험 전, 결과에 넣지 않는다

본 실험 시작 전에 과제와 무관한 가벼운 작업 2개를 준다. 목적이 하나: **도구를 만져보는 동안
생기는 낯선 느낌을 본 실험에서 빼는 것**이다. 참가자가 처음 본 도구를 더 느리게 다루는
것은 도구의 문제가 아니라 첫 접촉의 문제다.

손익 시나리오 기록은 **하지 않는다**. (손익을 보는 순간 사람들이 결과를 조작하려 들기 시작한다.)

## 4. 과제 — 고정 프롬프트

**반복마다 아래를 그대로 읽어 준다.** 다듬지 않는다.

```
아래 폴더에서 .ts 확장자이면서 2KB보다 큰 파일 중, 마지막 수정일이
가장 최근인 것 3개를 찾아 나열해라.

각 파일마다:
  - 경로
  - 마지막 수정 시각
  - 그 경로가 어디서 나왔는지 (원문 근거)

근거가 없으면 근거가 없다고 말해라. 지어내지 마라.
```

**두 팔(arm)**

| 팔 | 도구 구성 |
|---|---|
| A (기준선) | 원래 방식 — 참가자가 평소 쓰던 도구(ripgrep/find + sed 등) |
| B (후보) | parism |

**팔 순서는 참가자마다 교대한다.** 항상 A→B로 하면 두 번째 팔이 이전 실행의 기억을 이긴다.
(참가자 1,3,5,7은 A→B / 2,4,6,8은 B→A)

**두 팔 사이에 대화하지 못하게 한다.** B에서 arm A의 결과를 물어보면 그 기록은 버린다.

## 5. 1회 시도에서 기록하는 것 (과제당 5회)

시도 하나 = 위 프롬프트를 한 번 던지고, 사람이 **결과가 맞는지 확인하고 확정하는 것**까지.

| 기록 항목 | 채점 주체 | 정의 |
|---|---|---|
| `correct` | 기계 | 기대값과 **기계적으로 대조** (6장) |
| `wrong_kind` | 기계 | 틀렸다면 무엇이 틀렸나 (아래 분류) |
| `attempts` | 사람 | 결과를 확정하기까지 **같은 도구로 다시 시도한 횟수**. 1이면 추가 시도 없음 |
| `verify_seconds` | 사람 | 결과를 처음 읽은 순간부터 "이건 맞다" 하고 확정할 때까지의 시간. 추측하지 말고 타이머를 본다 |
| `gave_up` | 사람 | parism 팔에서 원래 도구로 되돌아가서 끝냈는가 (Y/N) |
| `reasons` | 사람 | Y면 이유를 한 줄. 그 한 줄이 다음 버전의 요구사항이다 |

**`wrong_kind` 분류** (고정 목록. 나중에 새 종류를 만들어 넣지 않는다)

| 코드 | 뜻 |
|---|---|
| `none` | 맞음 |
| `miss` | 조건에 맞는 대상을 놓침 |
| `extra` | 조건에 안 맞는 것을 넣음 |
| `wrong_order` | 대상은 맞는데 순서/개수가 다름 |
| `fabricated_evidence` | **근거가 원문에서 그 값을 가리키지 않음** — 가장 무거운 실패 |
| `silent_loss` | 빠진 대상에 대한 **사유가 없음** (조용히 사라짐) |
| `refused_wrongly` | 답할 수 있는데 거절함 |
| `timeout` | 시간 내 끝나지 않음 |

`fabricated_evidence` 와 `silent_loss` 는 **오답보다 무거운 실패**로 따로 센다.
맞는 값을 주되 그 근거가 거짓인 경우, 사람은 "맞았다"고 믿고 넘어가기 때문이다.

## 6. 기계 채점 — 사람이 매기지 않는 것

각 시도마다 참가자가 만든 **결과 파일**을 그대로 두고, 기계가 채점한다. 사람이 "맞았다"고
쓰는 대신 **기계가 대조한다.** 사람의 좋고 싫음과 정답을 분리하기 위해서다.

- 기대값: `experiments/lib/harness.mjs` 의 `expectedTsOver` 로 fixture 마다 미리 계산해 둔다.
- 대조: 경로 3개가 **순서까지** 일치하는지, 각 근거 바이트 구간이 원문에서 그 값을 가리키는지.
- 원문 대조는 바이트로 한다. 사람이 눈으로 확인한 것으로 통과시키지 않는다.

기계 채점이 끝나면 `scoringsheet.csv` 가 자동으로 채워진다. 사람이 손으로 옮겨 적는 단계가
없어야 전이가 잘못될 여지가 없다.

## 7. 절차 순서

1. 참가자마다 빈 디렉터리 하나를 준비한다(과제 fixture 복사본 — 서로의 것을 보면 안 된다).
2. 손님 시나리오 2개(3장). 기록 안 한다.
3. 팔 순서를 정한다(4장 교대 규칙).
4. **과제 1회 시도**를 진행한다. 사람이 타이머를 켠다.
5. 결과를 파일로 남기고 **기계 채점**한다. 대화는 이 시점까지.
6. `attempts` / `verify_seconds` / `gave_up` / `reasons` 를 **즉시** 적는다. (나중에 기억으로 채우면 지운다)
7. 3~6을 **5회** 반복한다. 같은 fixture를 쓴다.
8. 다음 과제로 넘어간다. 팔은 과제마다 다시 교대할지, 참가자 단위로 고정할지 **사전에 정한다. **
   기본값은 참가자 단위 고정이다 — 바꾸면 '팔 순서 효과'와 '과제 난이도 효과'가 섞인다.

**총 소요 시간**: 참가자당 5회 × 과제당 20~30분 + 준비/설명 30분.
1개 과제만으로도 피로가 크다. 30과제를 한 세션에 몰아넣지 말 것 — **과제를 3~5개 묶음으로 나눠
중간에 쉬고**, 쉬는 시간을 기록에 남긴다. 피로가 내려간 뒤의 시도와 다르다.

## 8. 하지 말아야 할 것

- **참가자에게 parism 의 목적을 말하지 않는다.** "근거를 강조한 도구"를 알고 있으면 과제를
  다르게 읽는다. 그냥 "셸 출력 구조화 도구"로만 소개한다.
- **중간에 힌트를 주지 않는다.** 힌트를 준 시도는 버린다. 아니면 그 시도는 정확도 분모에
  들어가고 분자가 아니게 된다.
- **실패한 시도를 지우지 않는다.** 가장 깨끗한 결과 1개만 남기고 버리면 정확도가 올간다.
- **참가자가 자기 결과를 직접 채점하게 하지 않는다.** 기계가 채점한다(6장).

## 9. 분석

`node experiments/human-study/analyze.mjs <scoringsheet.csv>` — 원시 집계와 신뢰구간을 낸다.
**판정은 하지 않는다.** 사람이 읽고 판단한다.

산출하는 것:

- 팔별 정확률 + **Wilson 신뢰구간** (작은 n 에서 정규 근사가 틀리므로 Wilson 을 쓴다).
- 쌍을 이룬 정확률 차이 + **부트스트랩 신뢰구간** (같은 참가자·같은 과제 쌍이므로 쌍 분석이 맞다).
- 시도 횟수 분포(중앙값, p90) — 평균은 한 명이 12번 시도한 값에 끌려간다.
- 확인 시간 분포. **분포를 보고 중앙값을 쓴다.** 평균 비교는 하지 않는다 — 3명이 5분씩
  멈춰 서 있었다면 평균은 아무 의미도 없다.
- `fabricated_evidence` / `silent_loss` 건수는 **정확률과 분리해** 낸다.
- 이탈자 수, 부작용 메모.

**표본이 부족하면 그 사실부터 말한다.** `n < 5` 면 분석 스크립트는 신뢰구간 대신
"표본이 이 결론을 지지하지 않는다" 를 출력한다. 숫자를 억지로 내지 않는다.

## 10. 이 결과를 어떻게 읽어야 하는가 (미리)

결론은 세 가지 중 하나일 가능성이 높고, **어느 쪽이든ublication 은 아니다**:

1. B 가 정확도에서 이겼다 → 근거가 없는 답을 줄였다는 것이고, 그게 이 도구의 존재 이유다.
   **확인 시간이 줄었다는 별도 증거가 있어야** "더 빠르다"고 말할 수 있다.
2. 정확도는 같고 확인 시간만 줄었다 → 여전히 쓸 만한 이유지만 작은 이유다.
3. 차이가 없다 → **이 실험이 실패한 것이지 도구가 실패한 것이 아니다.** 왜 안 나왔는지를 봐야 한다
   (과제 난이도가 낮았거나, 참가자가 parism 의 쓰임새를 제대로 못 찾았거나).
   이 경우 설계가 잘못된 것이고 다시 짜야 한다.

3번을 "도구가 별로다"로 읽으면 안 된다. **무엇이 안 나왔는지가 다음에 할 일이다.**
