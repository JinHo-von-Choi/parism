# 1단계 행동 검증 절차서 — "명령이 없다" 를 다음 행동으로 바꾸면 에이전트가 달라지는가

`@nerdvana/parism` 1단계(환경 인식 계층)의 성공 기준을 정하고 측정하는 문서다.

- 대상: `plan/feature-environment-awareness-1.md` TASK-014
- 스크립트: `experiments/environment-awareness-behavior.mjs`
- 결과: `experiments/environment-awareness/results-2026-10-22.json`
- 작성일: 2026-10-22

---

## 0. 이 측정이 답하려는 질문과 답하지 않는 질문

**답하려는 것**

1. 실행이 ENOENT 로 실패했을 때, 응답에 **설치 지시와 대체 명령**을 붙이면 에이전트의 다음 행동이
   "같은 명령 재시도" 또는 "포기" 에서 "설치" 또는 "대안 전환" 으로 **바뀌는가.**
2. 그 변화의 크기가 얼마인가.

**답하지 않는 것** — 이 측정으로 답하려 들면 안 된다

- **Terminal-Bench 성적.** harness 개선의 효과 천계가 있다. 1단계의 목표는 성적이 아니라
  **실패 모드("PATH 에 없음") 가 소멸하는 것** 이다.
- **parism 이 전체 벤치마크에서 좋은지.** 이 측정은 parism 이 아니라 *한 기능* 을 본다.
- **사용자 만족도.** 사람이 편하냐는 질문이 아니다.
- **에이전트 종류에 대한 일반화.** 여기서 재는 것은 **한 모델이 한 프롬프트에 한 선택을 하는 것** 이다.

**결론부터 말하면**: 이 측정은 **1단계가 잘 됐는지에 대한 증거**이지, 그 자체가 최종 판정이 아니다.
판정은 1~3절의 수치와 재현 절차가 함께 만든다.

## 1. 측정 설계

### 짝지 시험(paired)

같은 과제·같은 응답 틀을 **두 팔**에만 나누어 비교한다.

| 팔 | `failure` 의 내용 | 해당 버전 |
|----|-------------------|----------|
| `before` | `{ kind, reason, message }` | 게시된 v2.1.1 |
| `after`  | `{ kind, reason, message, errorCode, availability }` | 1단계 |

바꾼 것은 **오직 `availability` 필드 하나**다. 명령·인자·과제·프롬프트·모델·cwd 배너는 양쪽이 같다.
그래서 차이의 원인은 하나로 좁혀진다.

cwd 배너는 **양쪽 다** 넣는다. 배너까지 넣으면 비교 대상이 둘이 된다.

### 표본

이 호스트에서 **설치돼 있지 않은** 허용 명령만 쓴다. 2026-10-22 기준 6종이다.

```
tree, kubectl, helm, terraform, brew, pnpm
```

명령마다 **과제 상황 3개**를 만들어 18 쌍을 돌린다. 명령 6개만으로는 2pp 차이를 재지 못한다.

표본이 이 호스트에 의존한다는 한계가 있다. 다른 호스트에서 돌리면 다른 명령 집합이 되고
다른 수치가 나온다. **절차와 스크립트는 그대로 재현된다.**

### 지표

| 선택지 | 뜻 | 1단계의 목표 |
|--------|-----|--------------|
| A | 응답에 있는 설치 명령을 실행한다 | ✅ |
| B | 응답에 있는 대체 명령으로 전환한다 | ✅ |
| C | 같은 명령을 그대로 다시 시도한다 | ❌ |
| D | 멈추고 사용자에게 알린다 | ❌ (아직) |

**주 지표**: `A + B` 의 비율 — 실패가 **다음 행동으로 바뀌었는지**.
**보조 지표**: `C` (재시도 비율), `D` (포기 비율).

**판정선**: `A+B` 비율의 개선이 **2pp 미만**이면 설계를 재검토한다.

## 2. 절차

```bash
npm run build
node experiments/environment-awareness-behavior.mjs --out experiments/environment-awareness/results-2026-10-22.json
```

스크립트가 하는 일:

1. 이 호스트에 없는 허용 명령을 찾는다.
2. 각 명령·과제 조합에 대해 **실제 엔진**을 돌려 진짜 응답을 받는다.
3. `after` 팔은 그 응답 그대로, `before` 팔은 `errorCode` 와 `availability` 를 뺀 응답이다.
4. 각 팔에 대해 모델에 다음 행동 하나를 고르게 한다.
5. 선택 분포와 `A+B` 비율의 차이를 출력한다.

모델 호출은 `mcode exec` 로 한다.

```
mcode exec --model minimax/MiniMax-M3 --permission off --max-steps 1 \
          --output-format text --system-prompt-file <tmp> <prompt>
```

- `--max-steps 1` — 도구 호출을 막는다. 순수한 선택만 받는다.
- `--permission off` — 실행 권한이 없다.
- 매 시도마다 **새 세션**이라 앞선 시도의 맥락이 새지 않는다.
- 응답에서 첫 글자 하나(`A`/`B`/`C`/`D`)만 취한다.

**표본이 한 회차의 값이라는 사실을 감추지 않는다.** 같은 입력으로 다시 돌리면 다른 분포가 나올 수 있다.
아래 수치는 2026-10-22 의 그 회차다.

## 3. 결과

### 1차 측정 — npm 후보 관리자가 없을 때

`results-2026-10-22-pre-npm-candidate.json`

| 팔 | n | A 설치 | B 대안 | C 재시도 | D 포기 | 판독 불가 | **A+B** | C | D |
|----|---|--------|--------|----------|--------|------------|---------|---|---|
| before | 18 | 0 | 0 | 0 | 18 | 0 | **0.0%** | 0% | 100% |
| after | 18 | 1 | 7 | 0 | 10 | 0 | **44.4%** | 0% | 55.6% |

**변화: +44.4pp.** 판정선 2pp 를 크게 넘는다.

읽어야 할 것 두 가지.

1. **before 팔은 18개 전부 D(포기)다.** 재시도(C)는 0이고, 100% 가 멈췄다.
   즉 원래 parism 의 `spawn helm ENOENT` 는 에이전트를 **재시도하게도 만들지 못하고 포기하게 했다.**
   재시도 루프가 아니라 정보 부재가 문제였다.
2. **after 팔에서 여전히 D 인 10개가 있다.** 변환된 8개는 `tree`(대안), `helm`(대안),
   `kubectl`(설치), `pnpm`(대안)였다. **변환되지 않은 쪽에는 이유가 있다** — 다음 절.

### 측정이지 않은 것

이 측정은 **parism 의 정보가 에이전트의 다음 행동을 바꾸었다** 는 것을 보인다.
**설치가 실제로 성공했다** 는 것은 재지 않는다. 지시는 문자열이고, 그 실행과 성공은 별개다.

## 4. 1차 측정이 드러낸 결함

after 팔에서 포기(D)로 남은 10개를 명령별로 보면:

| 명령 | 이 호스트에서 쓸 수 있는 설치 경로 | 결과 |
|------|----------------------------------|------|
| `tree` | `apt install -y tree` | ✅ 변환됨 |
| `helm` | 없음 (대안 `kubectl` 로 전환) | ✅ 변환됨 |
| `kubectl` | `apt install -y kubernetes-client` | ✅ 변환됨 (1/3) |
| `pnpm` | **없음** (표에는 `npm install -g pnpm` 가 있으나 후보 관리자 목록에 `npm` 이 없었다) | ❌ |
| `terraform` | 없음 (HashiCorp 자체 저장소가 필요) | ❌ (옳은 결과) |
| `brew` | 없음 (자기 자신으로 설치되지 않는다) | ❌ (옳은 결과) |

`pnpm` 은 **표에 설치 방법이 있는데도 안내가 안 나간** 경우다. 원인은
`MANAGER_CANDIDATES` 의 linux 목록에 `npm` 이 없었다는 것이다. `npm install -g pnpm` 은
`npm` 이 있는 모든 호스트에서 방법이 있는데, 후보 목록에 없으니 **한 번도 시도되지 않았다.**

이건 측정 없이도 드러났어야 할 결함이었다. **측정이 설계 결함을 찾는 데에도 쓰였다** 는 점이
이 절차의 부수 가치다.

**수정**: linux·darwin 후보 관리자 목록 끝에 `npm` 을 넣었다.
시스템 패키지 관리자로는 node 패키지가 없거나 이름이 다르니 `npm install -g` 가 그 자리에 선다.

`terraform` 과 `brew` 의 포기(D)는 **옳은 결과**다. 설치 방법을 모르는 것이지 계층이 실패한 것이 아니다.
없는 방법을 지어내지 않는 대가가 "포기" 로 보이는 경우다. 그 대가는 감수한다 —
거짓 지시보다 낫다.

## 5. 2차 측정 — 수정 후

`results-2026-10-22.json`

| 팔 | n | A 설치 | B 대안 | C 재시도 | D 포기 | 판독 불가 | **A+B** | C | D |
|----|---|--------|--------|----------|--------|------------|---------|---|---|
| before | 18 | 0 | 0 | 0 | 18 | 0 | **0.0%** | 0% | 100% |
| after | 18 | 4 | 5 | 0 | 9 | 0 | **50.0%** | 0% | 50.0% |

**변화: +50.0pp.** 1차(+44.4pp) 보다 올랐다. 판정선 2pp 를 크게 넘는다.

명령별 전이(같은 18개 과제 쌍):

| 명령 | before | after | 무슨 일이 일어났는가 |
|------|--------|-------|--------------------|
| `tree` | D D D | **B B B** | 대체 명령(`find`)으로 전부 전환. 3/3 |
| `kubectl` | D D D | **A D A** | 설치 명령(`apt install -y kubernetes-client`)으로 2/3 전환 |
| `helm` | D D D | **B B D** | 대체 명령(`kubectl`)으로 2/3 전환 |
| `pnpm` | D D D | **A A D** | npm 후보 추가 덕분에 설치 명령(`npm install -g pnpm`)으로 2/3 전환 |
| `terraform` | D D D | D D D | 설치 방법이 없다. **여전히 포기** — 옳은 결과 |
| `brew` | D D D | D D D | 자기 자신으로 설치되지 않는다. **여전히 포기** — 옳은 결과 |

`tree` 가 3/3 으로 전부 전환된 것이 눈에 띈다. `tree` 는 대체 명령(`find . -maxdepth 3`)이
**같은 일을 정확히 대신할 수 있고**, 설치 명령(`apt install -y tree`)도 있다.
두 경로가 모두 있었던 명령이다.

`helm` 이 2/3 인 것은 설치 방법이 없어서다(공식 설치 스크립트는 셸 파이프라인이라 안내하지 않는다).
대체 명령만 있으므로 그쪽으로 갔다.

`terraform` 과 `brew` 의 3/3 포기는 **계층의 실패가 아니다.**
설치 방법을 모른다는 것을 모른다고 말한 결과다. 거짓 지시를 내는 대가다.
**없는 방법을 지어내지 않는 이상**, 이 두 명령의 전환률 0% 는 받아들여야 한다.

### 1차와 2차의 비교

| 측정 | before A+B | after A+B | 변화 |
|------|------------|-----------|------|
| 1차 (npm 후보 없음) | 0.0% | 44.4% | **+44.4pp** |
| 2차 (npm 후보 추가) | 0.0% | 50.0% | **+50.0pp** |

before 팔은 두 번 모두 0.0% 다. **이 계층이 없을 때 에이전트의 다음 행동은 항상 "포기" 였다.**
after 팔의 차이는 `pnpm` 이 `A` 를 선택하기 시작한 5.6pp 다. 설치 표를 고친 것이
측정에서 그대로 드러났다.

## 6. 재현 방법

- **환경**: 이 호스트(Ubuntu 24.04, Node 22, `minimax/MiniMax-M3`). 표본이 호스트에 의존한다.
- **모델**: `minimax/MiniMax-M3`. `PARISM_BEHAVIOR_MODEL` 로 바꿀 수 있다.
- **재현**: 위 2절의 두 줄. 결과 JSON 이 함께 저장된다.
- **재현성 한계**: 모델이 매 호출마다 다르게 답할 수 있다. **2절의 스크립트를 그대로 돌려
  같은 분포가 나오는지 확인하는 것이 재현성 확인이다.** 한 번의 실행 결과를 재현성이라고 부르지 않는다.

## 7. 결론

**1단계는 판정선을 넘었다.** `A+B` 비율이 0.0% → 50.0% 로, 판정선 2pp 를 크게 넘었다.
**설계를 재검토할 이유가 없다.** 다음 후보로 넘어간다.

재검토하지 않은 **남은 실패**를 분명히 적는다.

1. **포기(D)가 여전히 50% 다.** 설치 방법이 아예 없는 명령(`terraform`, `brew`)이 이 호스트의 절반이다.
   설치 표를 더 채우면 줄어들겠지만, **방법이 없는 명령을 늘리는 건 지어내기** 다.
   남는 선택은 두 가지다 — 그 명령을 쓸 수 있는 **대체 경로**를 더 찾거나,
   계층이 아니라 **환경 구성 문제**로 사용자에게 알리는 방법을 더 분명하게 하거나.
2. **변환이 일어난 비율이 아니라 변환의 종류를 재지 않았다.** `A`(설치)와 `B`(대안) 중
   어느 쪽이 더 나은 결과인지 이 측정은 말하지 않는다. `pnpm` 에서 `npm install -g pnpm` 가
   성공할지는 **이 측정 밖의 사실**이다.
3. **이 표본은 이 호스트의 6개 명령이다.** 다른 호스트에서 40개 전부를 포함해 돌리면
   분포는 달라진다. 절차는 재현되지만 **수치는 이 호스트의 값**이다.
4. **모델이 한 번 답한 것**이다. 같은 과제를 다른 모델, 다른 프롬프트로 돌리면 분포가 달라진다.

**다음 단계로 넘기는 조건**: 1단계는 통과했다. 2단계(MCP Apps)는 SDK v2 전환이 선행되어야 한다
(확인된 사실: `@modelcontextprotocol/ext-apps` 2.0.3 은 SDK v2 패키지 분할을 peer 로 요구한다).
3단계(Rust 정규식)는 `docs/regex-inventory.md` 의 게이트를 통과했다 — 옮길 대상에 lookaround 와
역방향 참조가 없다. 다만 **유니코드 경계 차이(`\b`) 처리 방식을 3단계 착수 전에 확정해야 한다.**
