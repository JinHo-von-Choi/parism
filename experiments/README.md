# parism 실험 하네스 — A·B·성능 게이트·사람 실험 절차·경쟁 도구 비교

작성자: 최진호
작성일: 2026-10-05

계획서 10장 "사용자 가치 실험" 의 두 실험을 **기계적으로 채점 가능한 부분**까지 구현했다.

```
npm run build
node experiments/experiment-a.mjs
node experiments/experiment-b.mjs
```

두 스크립트 모두 여기서 실행해 통과했다. **실측값이며 가설이 아니다.**

---

## 이 하네스가 재는 것과 재지 않는 것

**재는 것(기계 채점 가능)**

| | 측정 대상 |
|---|---|
| A | 정답 recall(기대값을 아는 fixture), 근거 존재·정확성, 예산 준수, 누락 내역 분리, 거절 사유 |
| B | 새로 생긴/해결된 이상 탐지, 필드 근거 부착, 순서·절단 상황에서의 거짓 변화 0, 보류 계약 |

**재지 않는 것(사람이 매겨야 한다)**

- 사람이 "이상"이라고 판단하는가
- 근거 확인에 실제로 걸린 시간
- 같은 정확성에서 토큰이 줄었는지, 그리고 줄어든 만큼 납득이 오르는지
- 경쟁 도구(jc 등) 대비 체감

**이 하네스가 숫자를 만들지 않는 것들을 숫자처럼 말하면 그것은 측정값이 아니라 추측이다.**

```
npm run build && node experiments/experiment-a.mjs
```

소스를 tsx 로 직접 실행하면 **이 호스트에서 `spawn(detached=true)` 가 ENOENT** 를 내 모든 명령이 `spawn_failed` 가 된다.

- 실측: 같은 인자로 `dist` 는 `find` 20건 정상 / tsx 소스 경로는 `spawn find ENOENT`
- 제품 결함이 아니다. 실험이 제품에 대한 측정치가 되려면 **제품과 같은 산출물**을 재야 한다.

## 부록 B. 실험 B — 전후에서 새로 생긴 이상 1건 + 해결된 1건 + 근거

### 영역 1: `git status --porcelain` — 비교가 **성립해야 하는** 경우

fixture:
```
=== 전(before) ===
 M b.txt   ?? c.txt
=== 후(after) ===
M  b.txt   A  c.txt
```

| | 전후 |
|---|---|
| 새로 생긴 이상 | `c.txt`: 미추적(`??`) → 스테이징(`A `) |
| 해결된 이상 | `b.txt`: 미스테이징(` M`) → 스테이징(`M `) |

### 팔 ①: 두 JSON 을 그대로 나란히

```
전 109 문자 / 후 109 문자
단순 JSON 비교로 어긋난 줄: 1줄
```

같은 37자 수인데 **한 줄이 어긋난 것으로 보인다.** 배열 순서와 인덱스가 얽혀 사람이 어디가 바뀌었는지 알 수 없다.

### 팔 ②: `compare_results`

```
comparable=true domain=git
added=0 removed=0 changed=2 unchanged=0
changed=[
  { label: ".../b.txt", status: "changed",
    changes: [ {field:"xy", before:" M", after:"M "},
               {field:"index", before:" ", after:"M"},
               {field:"worktree", before:"M", after:" "} ],
    base_pointer:"/0", current_pointer:"/0" },
  { label: ".../c.txt", status: "changed",
    changes: [ {field:"xy", before:"??", after:"A "}, ... ],
    base_pointer:"/1", current_pointer:"/1" } ]
```

`changed=2` 이고 **어느 행이 왜 바뀌었는지 + 원문 어느 위치인지**가 함께 나온다. `key` 같은 저장소 접두사가 아니라 `label` 로 읽을 수 있다.

### 영역 2: `kubectl get pods` — 비교를 **보류해야 하는** 경우

fixture:
```
=== 전 ===              === 후 ===
api-1  Running   0  5d   api-1  Running          0  5d
api-2  Running   0  5d   api-2  CrashLoopBackOff 7  5d
web-1  Pending   0  2m   web-1  Running          0  3m
```

`api-2` 가 crash-loop(재시작 0→7) 인 **새로 생긴 이상**, `web-1` 이 Pending→Running 인 **해결된 이상**이다. 사람이 보면 바로 알 수 있다.

그런데 parism 은 이렇게 말한다.

```
comparable=false domain=kubernetes changed=0
보류 사유: ["no metadata.uid: a recreated resource with the same name cannot be told apart from an existing one",
           "identity could not be established for some rows, so the comparison is withheld rather than reported as complete"]
```

**이것이 의도된 정답이다.** 표 출력에는 `metadata.uid` 가 없다. 이름이 같은 자원이 재생성된 것인지 이미 있던 것인지 구분할 수 없다. 다른 무엇을 놓쳤다고 단정하면 그것이 거짓 변화다.

사람이 눈으로 보면 `api-2` 의 CrashLoopBackOff 를 즉시 알아챈다. parism 은 그걸 **비교로 말하지 않고 보류로 말한다.** 취향의 문제가 아니라 계약의 문제다 — "이건 확실히 다른 자원이다"라고 말할 근거가 없다.

## 부록 C. 이 하네스가 잡은 결함 3건

하네스를 짜는 동안 제품 결함이 세 개 나왔다. **모두 하네스가 실제 저장소·실제 원문과 대조하다가 드러났다.**

### C-1. `retain: false` 로 발급한 id 의 거절 사유가 잘못됐다

`run` 은 `retain: true` 가 없어도 `review.result_id` 를 돌려준다(사용자가 `retained: false` 를 보고 안다). 그런데 그 id 로 `explain_result` 를 부르면 `unknown_id` 가 났다.

```
요청 안 함 → review.result_id = "r_..." , retained = false
explain_result("r_...") → unknown_id        ← '처음부터 보관 안 했다'는 사실이 사라짐
```

타입에는 `not_retained` 이 선언돼 있었지만 **어디서도 나오지 않았다.** `unknown_id`(이 세션이 모르는 id)와 `not_retained`(처음부터 보관하지 않음)은 원인이 다르다. 합치면 무엇을 해야 하는지 알 수 없다.

수정: `ResultStore.markNotRetained()` 추가, `retain: false` 일 때 그 사실을 기록. `explain_result` 는 `not_retained` 을 돌려준다. 회귀 시험 3건.

### C-2. git 행 identity 가 프로세스 cwd 에 의존했다

```
gitStatusIdentity({ path: "src/a.ts" }, "/tmp/xxx/repo", {}).key
→ "/tmp/xxx/repo /home/nirna/jobs/parism/src/a.ts"
```

`normalizePath` 가 `resolve(value)` 를 썼는데 `resolve` 는 **프로세스 cwd** 기준이다. 저장소 identity 가 파라미터로 넘어오면서도 쓰이지 않았다. 결과적으로 **같은 저장소의 같은 파일이 실행 위치마다 다른 key** 를 갖는다. 비교가 성립하지 않는 진짜 이유가 될 수 있다.

수정: 저장소 기준(`resolve(repoIdentity, value)`)으로 정규화. 회귀 시험 2건(상대/절대 경로 일치, cwd 비의존).

### C-3. `comparable` 이 항상 `true` 였고 `key_conflicts` 는 항상 빈 배열이었다

identity 를 확정하지 못한 행이 있어 `partial.withheld_reasons` 에 사유를 남기면서도 `comparable: true` 를 돌려줬다. "비교가 성립했다"와 "비교하지 못했다"가 동시에 말해지는 셈이다.

같은 자리에서 `key_conflicts` 를 빈 배열로 버리고 있었다. 중복 identity 를 찾아놓고 결과를 안 알려주면 조용히 한 행을 버린 셈이 된다.

수정: `comparable` 을 보류 사유 유무에 따라 계산하고, `key_conflicts` 를 실제 값을 돌려준다. 회귀 시험 2건.

### 부수 개선: `label` 필드

`CompareRowResult.key` 는 `저장소identity<NUL>경로` 형식이라 사람이 읽을 수 없다. 무엇이 변했는지 말하려면 이름이 보여야 하므로 `label` 을 함께 준다. **`key` 는 그대로 둔다** — 비교·대조용 식별자다.

## 부록 D. 하네스 작성 중 내가 낸 실수

제품 결함과 별개로, 하네스 자체가 여러 번 틀렸고 그때마다 제품이 정상인데 하네스만 실패했다.

| 실수 | 어떻게 알았나 |
|---|---|
| `withTemp` 가 비동기 콜백을 await 하지 않아 fixture 를 첫 실행 직후 삭제 | 첫 `spawn` 만 성공하고 이후 전부 `ENOENT`. `dir 존재` 를 찍어 발견 |
| `find` 접두사(`./`) 차이를 오답으로 셌다 | 경로 집합은 같은데 recall 이 0 |
| `find` 에 `evidence` 를 요구했다 | `find` 는 M1 근거 MVP 파서가 아니다. `ps`·`git porcelain` 이다 |
| `c.txt` 를 커밋해 버려 "미추적" 상태가 안 됐다 | `git add` 후에도 status 가 빈 것 |
| c.txt 를 커밋한 채 "미추적 → 스테이징" 을 기대했다 | 기대한 현상이 픽스처에 없음 |
| porcelain 출력 순서를 뒤집으려다 불가능함을 무시 | `git status` 는 경로순 정렬. 순서만 다른 입력을 만들 수 없다 |

**마지막 항목은 계획서 가정("순서 변화와 잘린 결과를 섞어")가 이 도메인에서 완전히 성립하지 않는다는 뜻이다.** git porcelain 은 경로순으로 정렬해 같은 파일 집합으로는 순서를 뒤집을 수 없다. 그래서 하네스는 "목록이 1건 늘어남"으로 그 자리를 대신 채우고 **그 사실을 코드 주석에 남겼다.**

## 부록 E. 아직 하지 않은 것

| 항목 | 이유 |
|---|---|
| 경쟁 도구(jc 등)와의 비교 | "해당 작업을 정상 지원하는 동일 조건에서만 비교"가 필요하다. 설치·판정 기준을 먼저 정해야 한다. **지원 범위가 다른 도구에 억지로 실패를 부여하지 않는다** |
| 5~8명 실험 실행 | 사람 개입이 필요하다 |
| 토큰 절감률 측정 | 현 fixture 에서 축약이 발생하지 않았다. fixture 를 키우고 예산을 낮춰야 하며 **절감 수치를 광고하기 전 5~8명 결과가 필요하다** |
| 30개 과제 · 5회 반복 | 실험 설계가 먼저다. 고정 모델·버전·온도·프롬프트와 confidence interval, 원시 집계 방법이 필요하다 |
| 성능 게이트(10% 회귀, 1KB/100KB/1MB × concurrency 1/4/16) | 별도 측정. 이번 하네스와 다른 성격 |

## 부록 F. 60초 데모에서 나온 것

`experiments/demo-60s.mjs` 가 계획서 11장의 세 장면을 그대로 재현한다. README 첫 화면에 넣은 값이 여기서 나온다.

### 실측값

| 장면 | 결과 |
|---|---|
| 1. 예산 | 200행 중 87행 표시, 119행 생략, measured 18355/20000, 파싱 오류 0건 |
| 2. 근거 | `git status` 는 `byte[3,13) = "changed.ts"`, `ls` 는 `source_kind: "none"` |
| 3. 이어 읽기 | 1회로 206행 전부 복원(중복 0), 명령 실행 1회 유지 |
| 그 뒤 | `unknown_id` 와 `not_retained` 을 구분해 거절, 재실행 없음 |

### 데모가 잡은 결함: 예산을 넘었는데 그 이유가 말되지 않았다

2,000 토큰 예산으로 이 목록을 부르면 **0행**이 나온다. 그런데 최종 payload 는 5,396 토큰이었다.

```
목록 206행 중 0행 표시
측정 5396 / 2000 토큰
omission: "206 of 206 row(s) were left out to fit 2000 tokens"   ← 이 문장만으로는 설명되지 않는다
```

행이 하나도 안 나갔는데 5천 토큰이 나왔다. **넘은 것은 행이 아니라 `raw` 원문**인데 omission 이 그 사실을 말하지 않아 '0행을 내보내면서 왜 5천 토큰이지' 알 수 없었다.

수정: `no row fits the budget with the required fields; the remaining N tokens are the response envelope and raw output, not rows`. 회귀 시험 1건.

### 계획서 예시값과 실측값이 다르다

계획서 11장은 "200개 중 28개 표시, 172개 예산 생략" 을 예시로 적었다. **실측은 87행 표시 / 119행 생략이다.** 예시값은 2,000 토큰 기준인데, 이 fixture 는 2,000 토큰으로 0행이 나온다(위 결함 참조). '일부는 표시되고 나머지는 사유와 함께 생략된다'가 보이도록 예산을 20,000 으로 잡았다.

**28 을 그대로 인용하지 않는다.** 화면 예시와 실제 반환량을 같은 것으로 말하면 그것는 거짓말이다.

## 부록 G. 성능 게이트 — 새 기능 off vs on (계획서 10장)

`node experiments/perf-gate.mjs` — 같은 커밋 안에서 `off`(새 인자 없음)와 `on`(근거+예산+보관) 두 경로를 재서, on 이 기존 경로에 **추가한** 비용을 공개한다. 1KB/100KB/1MB × concurrency 1/4/16.

### 측정 방법에서 먼저 밝혀야 할 것

- **같은 커밋의 두 경로만 비교한다.** 이전 커밋을 빌드해서 비교하면 빌드 차이와 코드 차이를 분리할 수 없다. "기능 off 회귀 없음"(이전 릴리스 대비) 판정은 이 스크립트가 하지 **않는다**.
- **명령을 두 개로 나눠 잰다.** 필드 근거를 실제로 만드는 파서는 `git status --porcelain` 과 `ps` 뿐이다. `ls` 만 재면 on 경로의 가장 무거운 비용(근거 구축)이 빠지고 "근거를 켜도 파싱 비용 정도다" 라는 잘못된 결론이 나온다. 그래서 `ls -l`(파싱·보관 비용)과 `git status --porcelain`(근거 구축 비용)을 나란히 놓는다. 표의 '필드근거' 열이 이 구분을 보여 준다.
- **concurrency 를 실제로 건다.** `max_concurrency` 값만 바꾸면 한 번에 명령 하나씩 부르는 한 아무 효과가 없다. concurrency 개를 동시에 띄우고 벽시계로 throughput 을, 개별 지연으로 p95 를 잰다. off/on 은 한 회차마다 번갈아 뛴다.
- **fixture 크기는 '만든 개수'가 아니라 '실제로 나온 stdout' 으로 확인한다.** 파일 이름 길이로 크기를 맞추려 한 첫 설계는 **실패했다**(파일명 255바이트 한계). 한 줄 길이는 작은 디렉터리에서 실제 명령을 돌려 재고, 만들어진 뒤 parism 으로 실제 크기를 다시 확인해 출력한다. 목표에서 0.5~2배 벗어나면 그 크기의 숫자는 보고하지 않는다.
- 표본이 작다(묶음당 10회). p95 는 최댓값에 가깝고 CPU 상태에 따라 움직인다. **여기서 통과/실패를 선언하지 않는다.**

4. **워커 CPU 는 측정하지 못했다.** 외부 ParserPack 이 있어야 측정되는 값이고 이 실험에는 없다. 수치를 지어내지 않는다.

이 표를 만들다가 **결과가 아니라 계약 위반에 가까운 두 가지 이차 비용**을 잡았다. 둘 다 M1·M2 가 들여온 경로였고, 값은 정확했지만 규모에서 무너졌다. 상세는 `docs/failure-cases-2026-10-05.md` 부록 A-7·A-8.

## 부록 H. 정확성 게이트 — seed 고정 변형 입력 (계획서 10장)

### 왜 이 게이트가 다른 실험과 다른가

다른 실험은 **측정하고 보고한다.** 이 스크립트는 **판정한다.** 하나라도 깨지면 `exit 1` 다.
그 차이를 벌린 이유는 계획서가 경계한 착오다 — *"무작위 입력에서 크래시가 안 나는 것만으로 파싱 정답이라 하지 않는다. 기대한 값을 알고 있는 fixture 가 반드시 필요하다."*

그래서 **생성기가 정답을 안다.** 각 변형을 만들면서 레코드 수와 경로 집합·원래 경로까지 함께 만든다.

```bash
npm run build && node experiments/corpus.mjs [--count=1200] [--verbose]
```

### 다섯 가지 판정

| 판정 | 무엇을 보는가 |
|---|---|
| 값 보존 | 만든 경로/명령이 **그대로** 돌아왔는가 (가공이 있었다면 그것도 드러난다) |
| 레코드 수 | 기대한 개수와 같은가 |
| 원문 범위 | 근거 바이트 구간이 원문 안에 있는가 |
| 명시적 unknown | 파싱될 수 없는 입력이 **조용한 빈 결과가 아니라 명시적으로 실패**하는가 |
| 민감 문자열 | 시크릿 canary 가 결과에 그대로 새지 않는가 |

### 실측

host: 72 cpu · node v24.15.0 · seed `20261005`

| 1,200 | **다섯 가지 전부 통과** |

전부 통과하는 게이트는 **고장 난 게이트와 구별되지 않는다.** 그래서 고친 결함을 되살려 게이트가 실제로 잡는지 확인했다.

| 되살린 결함 | 게이트 결과 |
|---|---|
| 이모지(서로게이트 쌍) 결함 | 192건 실패, exit 1 |
| 화살표 이름 변경 결함 | 14건 실패, exit 1 |
| 둘 다 고친 상태 | 0건, exit 0 |

회귀 시험도 같은 방식으로 확인했다(결함 3건을 되살려 7건 실패).

### 이 게이트가 **찾은** 것

두 건은 **제품 결함**이었고 고쳤다(세부: `docs/failure-cases-2026-10-05.md` A-10 · A-11).

- 따옴표 안의 경로를 UTF-16 코드 단위로 읽어 이모지가 U+FFFD 두 개로 깨졌다.
- 줄 모드 이름 변경의 구분자를 `lastIndexOf` 로 찾아, 새 경로에 ` -> ` 가 있으면 경로가 잘리고 닫는 따옴표가 값에 남았다.

### 이 게이트가 걸어서 발견한 **하네스 오류** — 결함이 아니었다

기록해 두는 이유가 있다. **생성기의 가정이 틀리면 그 차이를 파서 결함으로 잘못 읽게 된다.** 아래 네 건은 모두 그것이었다.

| 하네스 오류 | 오진한 내용 | 사실 |
|---|---|---|
| `ps` 행을 실제 `ps aux` 한 줄의 열로 지어냄 | "파서가 COMMAND 열을 3칸 밀어 읽는다" | `ps` 파서는 **컬럼 정렬이 아니라 공백 런(`\s+`) 기준**이다(`ps.ts:30`). 열 위치는 파서에 존재하지 않는 개념이므로 **그 계약을 흉내 낸 쪽이** 틀렸다 |
| 인용 조건을 `^ \| $`(앞뒤 공백)로만 검사 | "파서가 공백이 든 경로를 다르게 읽는다" | **실제 git 은 가운데 공백 하나만 있어도 인용한다**(실측 `A  "a b.txt"`). 생성기가 실제와 다른 출력을 만들어 넣었다 |
| 이름 변경 기대값을 두 모드에 똑같이 적용 | "이름 변경이 레코드를 삼키지 않는다" | **`-z` 에서만** 다음 레코드를 삼킨다. 줄 모드는 `orig -> new` 한 줄이다(`status-porcelain.ts:10-19`) |
| 파일 이름 조각에 NUL 을 넣음 | "-z 에서 경로가 잘렸다" | POSIX 경로에 NUL 이 없고 git 도 그런 출력을 내지 않는다. 파서가 구분자로 삼는 건 **옳은 동작**이다 |
| 명시적 실패 성공분을 `byCheck` (실패 카운터)에 올림 | "명시적 unknown 189건이 깨졌다" | 그 189건은 **잘한 것**이었다. 통과와 실패를 한 칸에 섞으면 **기계가 스스로 정확히 판단한 것까지 고장 보고**하게 된다 |

### 이 게이트가 **하지 않는** 것

- **두 파서만** 본다(`git status --porcelain`, `ps`). 나머지 40여 파서는 보지 않는다.
- **생성기가 만든 기대값**에서만 유효하다. 무작위 입력의 무사 마차가 아니다.
- **명령을 실행하지 않는다.** 합성 원문을 프로덕션 파서·근거 변환 함수에 직접 넘긴다(배선 자체는 1,400여 개 시험이 맡는다).
- 60초 데모(부록 F)나 성능 게이트(부록 F)를 대체하지 않는다. 시간과 정확성은 축이 다르다.

## 부록 I. `parism eval` — 판정을 세 층으로 (계획서 4.5장)

### 이 실험이 아니고 **제품**이다

다른 부록은 실험 하네스다. `parism eval` 은 사용자가 도는 명령이며, 깨지면 `exit 1` 이다.
그래서 실측과 함께 **고친 사실**을 남긴다.

### 결함 — 평가가 평가되지 않고 있었다

`parism eval` 은 `--help` 에 정상적으로 광고되었는데 **실행되지 않았다.** 등록만 하고 argv 라우팅을 빠뜨려서,
명령을 치면 **MCP 서버가 떴다가 exit 0 으로 끝났다.** 사용자에게는 성공으로 보였다.

진단 방법은 한 가지였다 — **stdin 을 열어두면 멈추는가.** 평가였다면 몇 초 안에 끝나야 한다.
멈췄다(실측 exit 124). 같은 조건의 `inspect` 는 즉시 끝났다.

세부: `docs/failure-cases-2026-10-05.md` A-13.

### 두 번째 결함 — 판정 하나가 세 가지를 덮고 있었다

예전 판정은 `result.ok` 한 개였다. 그 안에 host 존재 여부, 파서 보유 여부, 과제 성취가 모두 섞여 있었다.
가장 조용한 예: `node --version` 이 실패로 집계됐는데 실제로는 **가드가 정상적으로 막은 것**이었다.

| 층 | 무엇을 보는가 |
|---|---|
| `execution` | 명령이 **실제로 실행되었는가.** 가드 거절과 실행 실패를 구분한다 |
| `parse` | 구조로 읽었는가 · 파서가 없는 것 · 명시적 파싱 실패를 구분한다 |
| `task` | 자기 과제를 해냈는가. **없는 것을 찾는 과제는 실패해야 성공이다** |

### `retry-rate` 가 이름을 갖게 만들기

예전 "retry-rate" 는 `curl -I http://localhost:9999` 로 **이 호스트의 네트워크를** 재고 있었다.
재시도는 한 번도 세지 않았다.

이제 계약 하나를 직접 잰다 — **저장한 결과는 다시 실행하지 않는다.** 관측하려면
"다시 돌렸다면 값이 달라지는" 상황이 필요하므로, 빈 임시 저장소에서 결과를 보관한 뒤
**새 파일을 만든다.** 새 파일이 보이면 재실행이다. 시간을 두는 방법보다 확실하다 —
**관측이 추정에 의존하지 않는다.**

### 실측 (host 72 cpu · node v24.15.0)

```
── execution-parse ──
  층        기대있음  일치    관측
  execution      12   12/12    ran 11, blocked 2
  parse           3     3/3     parsed 10, parse_error 1
  task            2     2/2     succeeded 9, failed 2
── retry-rate ──
  task            2     2/2     succeeded 2
```

`blocked 2` 는 **가드가 일한 것**이다 — 경로 밖(`/tmp`)과 허용 목록 밖(`node`)을 각각 한 항목으로 둔다.
**명령 거절과 경로 거절을 같은 판정으로 뭉뚱그리지 않는 것**이 이 층 분리의 목적이다.

### 이 검사 중 드러난 함정 3가지

1. **임시 저장소가 경로 가드에 막혔다.** `allowed_paths` 기본값은 실행 디렉터리 하나다. 엔진은 실행 디렉터리를
   인자로 받지 않고 **설정 파일**로 받으므로, 그 경로가 든 설정을 넘긴다. 몰랐으면 "계약 위반" 이 아니라
   "가드에 막힘" 을 계약 위반으로 보고했을 것이다.
2. **명령 거절과 경로 거절이 같은 `blocked` 로 합쳐졌다.** `ls` 는 허용 목록에 **있는데** `/tmp` 가 밖이라 막혔다.
   처음에는 "parism 이 `ls` 를 못 실행한다" 고 읽었다.
3. **두 실패를 한 항목에 실었다.** `ls-missing` 이 "없는 파일"(task)과 "형식 미지원"(parse)을 함께 담아
   서로 다른 두 실패가 하나처럼 보였다. 나눴다.

## 부록 J. 토큰 비용 — 재현할 수 없던 수치를 다시 쟀다

### 이 부록이 없으면 README 가 거짓말을 한다

README 의 "솔직한 이야기" 절은 **재현할 수 없는 수치**를 인용하고 있었다.
`JSON 이 raw 보다 205% 무겁다`, `CFR 4.18% / 28.6%`, `설명 토큰 61% 감소` — 셋 다
출처로 든 `docs/plans/2026-03-06-benchmark.md` 가 **더 이상 존재하지 않았다.**

계획서 4.5장은 "LLM 오류 0%·CFR 0%·실측 아닌 추론시간 주장을 삭제하거나 시뮬레이션이라고
명확히 고치라"고 명시했다. 지우는 것으로 끝내지 않고 **되살렸다.**

### 되살릴 수 있었던 것과 그렇지 않았던 것

| 주장 | 처리 | 이유 |
|---|---|---|
| `CFR 4.18% / 28.6%` | **삭제** | 에이전트를 실제로 돌려야 재현된다. 이 저장소에서 불가 |
| `CFR 0%` (parism) | **삭제** | 한 번도 측정하지 않았다. 결정론 ≠ 정확 |
| 설명 토큰 `61% 감소` | **삭제** | 모델이 실제로 얼마나 쓰는지를 재야 한다. 여기서 불가 |
| JSON `205%` 무거움 | **재측정** | 토크나이저로 직접 잰다. **할 수 있었다** |

**재측정하면 되살릴 수 있는 것**을 지웠다면 그건 정리가 아니라 은폐다. 토큰은 잴 수 있었다.

### 실측 (host 72 cpu · node v24.15.0 · 토크나이저 `parism/approx`)

```bash
node experiments/token-cost.mjs [--entries=200]
```

| 항목 | raw 토큰 | JSON 토큰 | 차이 |
|---|---|---|---|
| 200 | 5,044 | 12,204 | **+142.0%** |
| 500 | 12,545 | 30,122 | **+140.1%** |

README 의 `205%` 와 **다르다.** 원인이 두 가지다 — 토크나이저가 명시되지 않았고, 원본 문서가
없어 어떤 항목 집합이었는지 알 수 없다. **같아야 할 수가 달랐다.**

**수치가 이제 문장이 아니라 스크립트다.** 다음 사람이 같은 명령을 돌리면 같은 값이 나오고,
다르면 그 다름을 설명할 의무가 생긴다.

### 투영 효과 96% 도 같은 처리를 받았다

README 의 투영 절은 "500개 항목에 `select`+`limit` 을 주면 응답 토큰이 **96%** 줄어든다
(28,609 → 1,066, gpt-tokenizer)"라고 적고 있었다. **이 수치를 내는 스크립트가 없었다.**
같은 부류의 문제였고 같은 방식으로 처리했다 — 스크립트에 측정을 추가하고 다시 쟀다.

```
투영(select name,size_bytes + limit 50)   ← 항목 500
투영 전 토큰   30122
투영 후 토큰   725
줄어든 비율    97.6%
```

**비교 대상이 다르다는 점을 출력에 명시했다.** 앞의 raw 대 JSON 표는 parism 응답과
`ls` 원문을 비교한 것이고, 여기는 parism 응답끼리 비교한 것이기 때문이다 — 차이를 만든
것은 투영이지 JSON 이 아니다. 두 축을 섞지 않아야 숫자가 오해받지 않는다.

README 의 값도 이 측정값으로 고쳤다(`parism/approx`, 같은 스크립트).

### 만들면서 만난 사실 — 파싱 결과의 모양이 크기에 따라 바뀐다

`ls -la` 의 파싱 결과가 **작은 목록과 큰 목록에서 다른 형태**였다.

```
작은 목록   { entries: [ {...}, {...} ] }
큰 목록     { entries: { schema: [...], rows: [ [...], [...] ] } }   ← 열형
```

최상위에서 배열을 찾지 못하고 키 개수를 세면 **항목 1개** 처럼 보인다. 실제로는 200개다.
항목 수를 잘못 적으면 그 아래 모든 비율이 **무엇 대비 무거운지** 를 잃는다 — 실측에서 이걸
놓쳤다가 고쳤다. **사이즈가 성능에 미치는 영향**을 재는 실험이라면 파싱 결과의 모양이
작업량에 따라 바뀐다는 사실을 함께 적어야 한다.

## 부록 K. 예산·의미 diff 게이트 — M2·M3 종료 조건을 실제로 잰다

### 이 게이트가 없었던 이유

M2·M3 의 종료 조건은 문서에 "통과"로 적혀 있었지만 **측정된 적이 없었다.**
단위 시험이 있다는 것과 조건이 참이라는 것은 다른 말이다. `corpus.mjs` 가 파서 정확성을
재듯, 여기는 예산과 diff 의 계약을 잰다. **그리고 첫 실행이 곧 결함 하나를 찾아냈다.**

### 게이트가 처음 잡은 것 — A-17

`max_tokens: 1400` 를 주었는데 **실제 전달이 1,939 토큰(상한의 138%)** 이었고,
`budget_met: true` 라고 했다. 예산 보고와 누락 목록이 **검색이 끝난 뒤에** 붙어서 그런 거였다.
계획서 M2 가 명시한 **"최종 상한 검증"** 이 아예 없었다. 상세는 `docs/failure-cases-2026-10-05.md` A-17.

### 판정 항목

| 항목 | 무엇을 보는가 |
|---|---|
| 예산 정합 | `measured_tokens` 가 **실제로 받는 응답의 토큰 수와 같은가**, `budget_met` 이 그 값에 대해 참인가 |
| 값 복원 | 빠진 행이 커서로 **다시 오는가** |
| 필수 필드 | `required_fields` 가 남긴 **모든 행** 에 있는가 (100%) |
| silent-loss | 빠진 행이 **반드시 omission 으로 선언**되는가 |
| 거짓 삭제 | 값이 그대로인데 diff 가 '변경' 이라 하지 않는가 |
| 대상 거절 | **다른 명령**의 결과끼리 비교하지 않는가 |
| key 충돌 | key 가 겹치면 조용히 넘어가지 않는가 |

### 재지 **않는** 것 — 분명히 적어 둔다

- **"순서만 변경하면 diff 0"** 은 여기서 재지 않는다. 같은 명령을 두 번 돌려서는 순서만 다른
  동일 내용을 만들 수 없다 — 만들려고 했다가 파일 이름을 바꿔야 했고, 그건 순서 변경이 아니라
  이름 변경이었다. **억지로 만든 조건으로 게이트를 채우지 않는다.** 이 조건은 단위 시험이
  맡는다(`tests/engine/compare.test.ts` "행 순서만 바뀌면 변화 0").
- **사람 실험의 `silent_loss`** 도 재지 않는다. 그것은 에이전트가 조용히 값을 잃었는가 라는
  질문이고 사람이 답해야 한다. 게이트가 재는 것은 **엔진이 omission 으로 알렸는가** 다 — 다른 질문이다.

### 실측

```bash
node experiments/budget-diff-gate.mjs [--cases=12]
```

12종 통과(exit 0). 결함을 되살리면 14건 실패(exit 1).

- **유의성 검정을 하지 않는다.** 5~8명으로 할 수 없다. 구간을 붙이되 그것이 유의성이 아님을 문서에 적었고, n<5면 구간을 내지 않는다.
- **평균을 쓰지 않는다.** 확인 시간은 중앙값과 p90 을 쓴다 — 3명이 5분씩 멈춰 서 있으면 평균은 그 3명에 지배된다.

`analyze.mjs` 는 합성 데이터로 경로를 전부 확인했다(빈 시트 / 정상 / 표본 부족 / 헤더 없음).
헤더가 없으면 열이 밀려 엉뚱한 숫자가 나오므로 **막고 종료한다** — 조용한 쓰레기가 이 프로젝트가
가장 경계하는 실패이기 때문이다.

## 부록 M. 경쟁 도구 비교 — RT / jc / Nushell

`node experiments/competitive.mjs` — 계획서 10장 "RT/jc/Nushell 은 해당 작업을 정상 지원하는
동일 조건에서만 비교하고, 지원 범위가 다른 도구에 억지로 실패를 부여하지 않는다" 의 실행.

**이전까지 "도구가 이 호스트에 없어 미실측" 이었다. 그 말은 이제 옛말이다** — jc 와 Nushell 을
실제로 설치해 쟀다. RT 는 **여전히 특정하지 못했다** — 어떤 도구인지 특정하지 못했으므로
추측으로 다른 도구를 대신 넣지 않고 비교에서 뺐다.

### 도구 준비 (시스템에 설치하지 않고 임시 위치에 둔다)

```bash
python3 -m venv /tmp/cmp-venv && /tmp/cmp-venv/bin/pip install jc
curl -sL -o /tmp/nu.tar.gz https://github.com/nushell/nushell/releases/download/0.116.1/nu-0.116.1-x86_64-unknown-linux-gnu.tar.gz
tar -C /tmp -xzf /tmp/nu.tar.gz
# 다른 위치라면 환경변수로 알린다
CMP_JC=... CMP_NU=... node experiments/competitive.mjs
```

도구가 없으면 그 팔은 **'측정하지 않았다' 로 보고하고 종료**한다. 성공률 0% 가 아니다.

### 실측 (host: 72 cpu · node v24.15.0 · jc 1.26.0 · nushell 0.116.1)

조건: `.ts` 이면서 2,048B 초과, 그중 **큰 순 3개** — 실험 A 와 **동일 fixture·동일 질문**.
기대값은 사람이 아니라 하네스 코드가 계산한다.

| 팔 | 소요 | 출력 바이트 | 기대 3개 | 큰 순 | 원문 근거 |
|---|---|---|---|---|---|
| raw (도구 없음) | 10.2ms | 584 | 3/3 ✓ | 불일치 | 좌표 없음 |
| 기존 Parism (근거·예산 없음) | 33.2ms | 584 | 3/3 ✓ | 불일치 | 좌표 없음 |
| 새 Parism (budget+evidence) | 19.0ms | 584 | 3/3 ✓ | 불일치 | 없음 (**review 가 알림**) |
| 새 Parism + 순위화 (조합) | 13.2ms | 190 | 3/3 ✓ | **일치** | 없음 (review 가 알림) |
| jc | 168.4ms | 1,326 | **측정 불가** | **측정 불가** | 좌표 없음 |
| nushell | 34.1ms | 307 | 3/3 ✓ | **일치** | 좌표 없음 |

### 이 표가 말하는 것

**1. Nushell 이 이 과제에서 가장 잘한다.** 한 파이프라인으로 조건·정렬·상위 3개를 끝내고
(`ls **/*.ts | where size > 2047b | sort-by size | last 3 | reverse`),
가장 작은 관련 출력(307바이트), 순서까지 맞는다. 파이썬을 쓰지 않는다.
**parism 이 이기지 못했다.** 이 사실을 감추지 않는다.

**2. parism 은 구조화까지만 하고 순위화는 호출자가 한다.** 조합 팔을 따로 둔 이유다 —
조합하지 않은 팔과 조합한 팔을 한 표에 섞으면 조합의 대가가 사라진다. 조합하면
13.2ms / 190바이트로 순서까지 맞는다.

**3. jc 는 이 과제를 정상 지원하지 않는다 — 측정이 아니라 구조의 문제다.**
- `jc --find` 는 `path` 와 `node` 만 준다. **크기가 없다.** '큰 순 3개' 를 낼 수 없다.
- 직접 부르면 빈 배열이 나온다: `jc --find find …` → `[]`. **stdin 으로 먹여야** 파싱된다
  (`find … | jc --find`).
- 파싱은 되지만 순위화가 다른 도구의 몫이 되고, 출력은 1,326바이트로 가장 크고 가장 느리다(168ms).
- 계획서 규칙대로 여기 '성공률 0%' 을 쓰지 않고 **'측정 불가'** 로 적었다.

**4. 이 과제에서 parism 에도 필드 근거가 없다.** 근거를 내는 파서는 `git status`·`ps` 뿐이다.
그리고 parism 은 그것을 **조용히 감추지 않는다** — `review` 경고로 알린다
(`this parser produces no field evidence yet`). 표의 '없음 (review 가 알림)' 이 그 실측이다.
**'조용히 없는 것' 과 '없다고 말한 것' 은 전혀 다르다.** 근거 열은 선언이 아니라
`explain_result` 로 되짚어 확인했다.

**5. "원문 근거" 열이 '좌표 없음' 인 도구를 나쁘다고 읽으면 안 된다.** 그 도구는
애초에 좌표를 주지 않는 설계다. parism 의 근거가 바이트 구간인 것은 설계 선택이고,
그 선택이 이 과제에서 아무 값도 못 냈다는 것도 사실이다.

### 이 표가 말하지 **않는** 것

- 사람이 매기는 지표(확인 시간·시도 횟수·포기 여부)가 아니다. 그건 `experiments/human-study/`.
- 이 표는 parism 이 우세함을 보여 주지 **못한다**. 보여 주려고 해도 안 된다.
- **RT 는 비교에 없다.** 특정하지 못했다.
- 한 번의 실행이다. 표본 1회이며, 위 숫자는 그 회차의 값이다.

### 조합 팔이 실제로 쓴 명령

```
jc        : find . -type f -name '*.ts' -size +2047c -print | jc --find
nushell   : ls **/*.ts | where size > 2047b | sort-by size | last 3 | reverse | to json --raw
```

'지원한다' 의 근거는 이 조합식이다. 어떤 도구를 어떤 조건으로 불렀는지가 없으면
비교는 의미가 없다.
