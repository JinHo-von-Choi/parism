# parism 실패사례 — 실측으로 잡은 결함과 재현되지 않은 주장

작성자: 최진호
작성일: 2026-10-05

이 문서는 **실측으로 확인한 결함**과 **재현하지 못한 채 손대지 않은 주장**을 함께 둔다. 두 번째 부류가 이 문서의 더 중요한 절반이다. 계획을 읽고 고쳐도 되지만, **재현하지 못한 것을 고쳤다고 말하면 그것은 측정값이 아니라 추측이다.**

모든 수치는 이 호스트(Linux 6.8, Node 24.15, `@nerdvana/parism` 2.0.2 기준선)에서 측정했다.

---

## 부록 A. 재현해서 고친 결함

### A-1. 외부 팩 계약 정규식이 메인 스레드에서 실행됨 (서버 정지 위험)

**증상.** 외부 ParserPack 하나를 등록한 뒤 그 팩이 다루는 명령을 호출하면, 워커 시간 상한(기본 500ms)이 **90초 넘게** 무시된다. 프로세스가 `EXIT=124` 로 타임아웃되어 죽는다. 서버 스레드가 멈추므로 다른 요청도 함께 멈춘다.

**재현 입력.** 팩 계약에 `noise: /^(a+)+b$/`. 40자 `a` 를 `echo` 로 넘긴다.

**원인.** 워커가 팩 모듈을 격리 실행해 계약 선언을 넘기면서, 정규식(`noise`·`rowLine`·`acceptedValues`)을 **`RegExp` 객체 그대로** 직렬화해 메인 스레드에 보냈다. 메인 스레드가 그것을 실행했다. 팩이 선언한 재귀 역추적 패턴은 워커 안에서는 시간 상한에 걸려 멈추지만, **메인 스레드에서는 시간 상한의 통제를 받지 않는다.**

**수정.** 계약 정규식 평가를 워커 안으로 옮겼다. 워커가 원문 줄 분류(`dataLines`·`rowLines`)와 플래그 값 판정(`valueVerdicts`)을 수행하고 **개수와 참/거짓만** 돌려준다. 메인 스레드는 서술자 `{ __parism_regex__: { source, flags } }`만 받고 `RegExp` 를 만들지 않는다. 판정 결과가 없으면 형식을 거절한다 — 검증 없는 통과를 막는다.

**실측 전후.**

| | 수정 전 | 수정 후 |
|---|---|---|
| 40자 입력 호출 | 90초+ (종료 안 됨) | 시간 상한에 걸려 `parser_exception` |
| 전체 호출 합계 | 종료 불가 | 1.5초 |
| 메인 스레드 다른 요청 응답 | 멈춤 | 0.99ms |

**회귀 시험.** `tests/parsers/external-isolation.test.ts` — catastrophic backtracking 정규식이 있어도 호출 하나는 시간 상한 안에 끝난다.

### A-2. 리댁션을 켰는데 기본 패턴이 전혀 적용되지 않음 (비밀 유출)

**증상.** `guard.secrets.output_redaction_enabled: true` 로 켰는데 합성 비밀 5종이 **전량 그대로 반환**된다.

| 합성 입력 | 기대 | 실제 |
|---|---|---|
| `sk-` + 32자 | `[REDACTED]` | `sk-aaaa…` (그대로) |
| `ghp_` + 30자 | `[REDACTED]` | 그대로 |
| `AKIA` + 16자 | `[REDACTED]` | 그대로 |
| `xoxb-` + 10자 | `[REDACTED]` | 그대로 |
| `glpat-` + 20자 | `[REDACTED]` | 그대로 |

**원인.** 설정 로더가 `guard.secrets.output_patterns` 의 **기본값을 `[]`** 로 두었다. 사용자가 키를 생략하면 "값이 없다"가 아니라 "의도적으로 비활성"이 되어 기본 패턴 7개가 아예 쓰이지 않았다. SPECIFICATION이 원래 문서화하던 계약("`undefined` 이면 7개 DEFAULT 패턴, `[]` 이면 레덕션 비활성")에 코드가 맞지 않았다.

**수정.** 기본값을 두지 않게 바꿨다. 생략하면 기본 패턴을 쓰고, `[]` 를 명시하면 의도적 비활화로 구별된다.

**부수 발견 (같은 원인).** `mergeGuardConfig` 가 `secrets` 를 하위 키로 병합하지 않아, `output_redaction_enabled` 하나만 켜면 `secrets` 객체가 통째로 갈아끼워져 `env_patterns` 기본값 6개가 사라졌다. **자식 프로세스 환경 변수 시크릿 제거가 통째로 꺼졌다.** `secrets` 도 하위 키로 병합하도록 바꿨다.

**주의.** 이 수정은 **breaking change** 다. 이전에 키를 생략하고 리댁션을 켠 사용자는 실제로 가려지지 않은 값을 보고 있었다. 되돌리려면 설정에 `output_patterns: []` 을 명시해야 한다.

### A-3. compact 가 값을 조용히 잃음 (세 가지)

**증상 1 — 구분자 평탄화.** 중첩 배열을 구분자 문자열로 이어 붙여 `["a|b","c"]` 와 `["a","b","c"]` 가 **모두** `"a|b|c"` 가 되었다. 복원 불가다.

**증상 2 — 값이 섞인 배열의 타입 소실.** 배열 안의 `null` 은 문자열 `"null"` 이 되고 객체는 `"[object Object]"` 가 되었다. 그리고 **객체 뒤에 `null` 이 섞인 행 배열**(예: 49개 객체 + `null`)에서 `TypeError: Cannot read properties of null` 로 프로세스가 죽었다. 순환 참조와 `BigInt` 값도 `TypeError` 였다. 헤더가 하는 포맷 변환 하나가 실행 전체를 중단시킬 수 있었다.

**증상 3 — 첫 항목만 보고 형식을 결정.** `[{a:1},"str"]` 에서 두 번째 행이 `[null]` 이 되어 조용히 사라졌다.

**수정.** `src/parsers/compact.ts` 를 전(total) 함수로 다시 썼다. `CompactOutcome`(`{ok:true,value}` \| `{ok:false,reason,message}`)을 돌리고,
- 값이 섞인 배열은 **압축하지 않고** 그대로 둔다.
- 모든 행의 유형을 확인한 뒤 섞여 있으면 압축하지 않는다.
- 순환 참조·`BigInt`·깊이 64 초과는 `representation_not_lossless` 로 **실패로 보고한다.**

엔진은 그 경우 압축을 적용하지 않고 **원형 JSON 과 `stdout.raw` 를 모두 남긴다.** `failure = { kind: "parse", reason: "representation_not_lossless" }`.

**이것은 breaking change 다.** `toCompact()` 는 `unknown` 대신 `CompactOutcome` 을 돌린다.

### A-4. `find`/`du` 가 파일명 끝 공백을 지움

**증상.** 줄 구분자로 나눈 뒤 경로에 `trim()` 을 적용했다. `report ` 가 `report` 로, `dir /inner  ` 가 `dir /inner` 로 바뀌었다. **다른 경로로 오인될 수 있는 손실**이다.

`find -print0` 경로는 원래 정확했으나 줄바꿈 경로가 아니었다. **같은 파일이 출력 방식에 따라 다른 값을 냈다.**

**수정.** 두 경로에서 `trim()` 을 제거했다.

---

### A-5. `kubectl get pods` 의 RESTARTS 열 밀림

**증상.** 재시작 횟수가 0이 아니면 kubectl 이 `2 (5d ago)` 처럼 괄호 표기를 RESTARTS 뒤에 붙인다. 이를 한 열로 세어 다음처럼 읽었다.

```
age: "(5d"   ip: "ago)"   node: "8d"
```

**수정.** 닫는 괄호까지를 RESTARTS 값으로 묶고 그 다음 칸을 AGE 로 읽으며, 괄호 표기를 `last_restart` 로도 보존한다.

### A-6. `git status --porcelain` 에 `-z` 없이 주면 모든 항목이 하나로 뭉침 (**M1 이 만든 회귀**)

**증상.** M1 에서 `--porcelain` 을 NUL 레코드 전용 파서로 보냈다. 그런데 `-z` **없이** 주면 출력은 줄 구분 + C 이스케이프 + 따옴표 형식이다. 파서는 원문 전체를 한 레코드로 읽었다.

**실측 원문** (개행·따옴표·탭·화살표가 든 파일 이름 저장소).

```
 M mod.txt
R  old.txt -> new.txt
?? "arrow -> x.txt"
?? "line\nbreak.txt"
?? "quote\"dq.txt"
?? "tab\there.txt"
```

**수정 전 결과: 항목 1개.**

```json
{ "xy": "RM", "index": "R", "worktree": "M",
  "path": "keep.txt -> renamed.txt\n?? \"line\\nbreak.txt\"\n?? ... 전부" }
```

7개 항목이 1개로 합쳐지고 `path` 에 개행과 ` -> ` 표기가 그대로 남았다. **조용히 틀린 값**이다 — 실패도 아니고 경고도 없다.

**수정.** `-z`/`--null` 유무로 판별해 세 가지를 나눠 처리한다.

| | `-z` 없음(줄 모드) | `-z` 있음(NUL 레코드) |
|---|---|---|
| 레코드 경계 | 개행 | NUL |
| 경로 해석 | C 이스케이프 해제 | 가공 없음 |
| 이름 변경 | 한 줄의 `원래 -> 새` | **새 경로가 먼저**, 원래 경로가 다음 레코드 |

화살표는 **오른쪽에서** 찾는다 — 경로 자체에 `' -> '` 가 들어갈 수 있기 때문이다. 줄 모드에서만 항목에 `quoted: true` 를 붙여 **출력이 가공되었음을 값으로 밝힌다.** 두 형식의 `path` 값은 같아야 한다(원래 파일 이름).

**수정 후 실측.**

| | `-z` | 줄 모드 |
|---|---|---|
| 항목 수 | 6 | 6 |
| 경로 집합 | 동일 | 동일 |
| 근거 바이트 구간 | 25개 전부 원문 정확 | 25개 전부 원문 정확 |
| 빠진 근거 포인터 | 0 | 0 |

**이 수정이 두 번 만에 틀린 값을 냈다는 점이 중요하다.** 첫 수정은 rename 항목이 통째로 사라졌다(`readPath` 가 끝 경계를 몰라 `원래 -> 새` 의 왼쪽 경로를 통째로 읽었다). 두 번째 수정이 고쳤다. 프로브가 매번 실제 저장소로 원문 대조를 하지 않았으면 놓쳤을 것이다.

**회귀 시험.** `tests/parsers/git-status-porcelain.test.ts` — 10건 추가(줄 모드 파싱, 이스케이프 해제, 화살표 안 잘림, 두 형식 경로 집합 일치, 근거 바이트 대조, `-z` 여부가 경계를 정함).

## 부록 B. 재현하지 못해 손대지 않은 것

**이 부록이 더 중요하다.** 계획서나 이전 검토에 있던 주장을 **재현하지 못했다.** 그러니 고치지 않았고, 고쳤다고 말하지도 않는다.

### B-1. grep 콜론 포함 파일명 유실

**주장.** `grep` 출력이 `파일:내용` 형식이므로 파일 이름에 콜론이 있으면 필드가 어긋난다.

**재현 시도.** 콜론이 든 파일 이름으로 `grep -r` 실행.

**결과.** 재현되지 않았다. `unknown` — 이 호스트의 grep 버전·로케일·인자 조합에서 그런 출력을 만들지 못했다. **어느 버전에서 재현되는지는 모른다.** 손대지 않았다.

### B-2. `find -print0` 로 개행 든 파일 이름 유실

**주장.** `find` 가 `-print0` 을 주지 않으면 개행이 든 파일 이름에서 줄이 깨진다.

**재현 시도.** 개행·탭·따옴표가 든 파일 이름 저장소에서 비교.

**결과.** 이미 정확했다. `-print0` 경로는 원래 올바르게 동작했고, **어긋난 쪽은 줄바꿈 경로였다**(A-4). 주장이 방향을 잘못 짚었다. 줄바꿈 경로만 고쳤다.

### B-3. macOS `stat` UID

**주장.** `stat` 파서가 macOS 의 `Uid` 표현을 못 읽는다.

**결과.** 재현 불가 — 이 호스트는 Linux 다. **판단하지 못했다**(`unknown`). macOS 에서 검증하기 전까지 손대지 않는다.

### B-4. `_summary` 필드 충돌

**주장.** 파서가 내는 `_summary` 와 서버가 붙이는 `_summary` 가 충돌한다.

**결과.** 재현되지 않았다. 현재 코드 경로에서 충돌하는 조합을 찾지 못했다.

### B-5. `parism eval` 진입점 누락

**주장.** `parism eval` 명령이 없다.

**결과.** **진입점은 존재했다.** 다만 `retry-rate`/`completion` 시나리오 2개가 비고(footnote) 4/7로 가드 사유 때문에 실패했다. 진입점 부재라는 주장은 **틀렸다.** 시나리오 실패는 별개 문제로 기록만 한다.

## 부록 C. 계획서 주장과 실측 결과의 차이

| 계획서 주장 | 실측 | 조치 |
|---|---|---|
| 외부 팩 ReDoS 가 워커 상한 500ms 를 90초+ 초과 | **그대로 재현** | 고쳤음 (A-1) |
| 리댁션 기본 패턴 미적용, canary 5종 전량 유출 | **그대로 재현** | 고쳤음 (A-2) |
| compact 구분자 평탄화·null 혼합 TypeError | **그대로 재현** | 고쳤음 (A-3) |
| find/du 후행공백 손실, kubectl RESTARTS 열 밀림 | **그대로 재현** | 고쳤음 (A-4·A-5) |
| grep 콜론 파일명 유실 | 재현 안 됨 | 보고만 (B-1) |
| `find -print0` 개행 파일명 유실 | 이미 정확 / 방향 오류 | 줄바꿈 경로만 (A-4, B-2) |
| macOS stat UID | 판정 불가 | 보고만 (B-3) |
| `_summary` 충돌 | 재현 안 됨 | 보고만 (B-4) |
| `parism eval` 진입점 누락 | **진입점 존재** | 보고만 (B-5) |

**재현된 4건이 아니라 5건이다** — `kubectl` 와 `find/du` 가 계획서에서 한 항목으로 묶여 있었지만 서로 다른 파서였다. 그리고 **재현 안 된 5건 중 1건(B-5)은 계획서 주장 자체가 틀렸다.**

## 부록 D. 이번 작업에서 실측이 잡은 내 결함

자기 검토다. 계획을 지켰다고 끝내지 않고, 실측이 코드의 결함을 드러낸 사례.

| 결함 | 어떻게 잡혔나 |
|---|---|
| 스테이징 안 됨(`" M src/a.ts"`)이 `RECORD` 정규식에서 거절됨 | M1 근거 대조 중 `" M src/a.ts"` 가 유실됨을 발견. 문자 클래스에 공백 추가 |
| `ps` 정규식의 `\\` 이스케이프 유실 | 근거 바이트 대조 중 원문과 불일치. 복원 |
| 숫자 근거 대조를 문자열로 함 | `"0.0"` 과 `0` 이 근거 불일치. 수치 비교로 수정 |
| **예산을 계산하고도 응답에 반영하지 않음** | M2 수용 기준①(final payload 상한)이 실패로 드러남. 표면만 붙고 본문은 그대로였음 |
| **본문만 재서 최종 payload 가 상한 초과** (measured 1481 > 1400) | 표면(누락 내역·진행 정보)을 붙인 뒤 최종 크기로 재야 한다는 사실을 실측이 알려줌. 전체 응답을 후보마다 재도록 변경 |
| `shrunkParsed` 내부 필드가 응답으로 새어나감 | 예산 경로 점검 중 발견. 제거 |
| **identity 미확정 행이 있는데 다른 쪽에 키가 안 보이면 `added` 로 단정** | M3 "거짓 삭제 0" 조건이 삭제 쪽에만 적용돼 있었음. presence 주장 보류(`canClaimPresence`)로 수정. 삭제 쪽도 동일 사유로 보류 |
| `--porcelain` non-`z` 항목 뭉침 (A-6) | tarball smoke test 의 2차 실행에서 발견 |

**"수용 기준을 정의해 두면 실측이 어긋난 자리를 알려준다"가 이 표의 요지다.** 위 여덟 건은 모두 내가 쓴 기준이 잡아낸 것이다.

## 부록 E. tarball 소비 smoke test 에서 나온 것

`npm pack` 한 tarball 을 클린 디렉터리에 설치하고 **설치본만** import 해서 12개 항목 31개 검사를 돌렸다. 전부 통과했다.

**발견 1 — 패키지 결함으로 단정하지 않은 것 (보고만).** `package.json` 의 `exports` 맵에 `./package.json` 과 `require` 조건이 없다. `require.resolve('@nerdvana/parism/package.json')` 이 막힌다. ESM 전용 패키지이므로 `require` 해석이 막히는 것은 **의도된 것**으로 보고, 소비자가 버전 확인을 위해 그 패턴을 쓰는 경우가 있다는 사실만 기록했다. exports 맵에 `./package.json` 을 열지는 **하지 않았다** — 스모크 스크립트를 우회하는 것으로 충분하고, 공개 계약을 늘리는 일은 이번 범위가 아니다.

**발견 2 — 사용 방식의 함정 (실측 사실).** `createEngine({ configPath })` 는 다층 설정 대신 `loadConfig` **단일 층**을 쓴다. 그래서 `PARISM_ALLOWED_PATHS` 같은 **환경변수 레이어가 반영되지 않는다.** 허용 경로를 설정 파일에 직접 적어야 한다. 기본 `allowed_paths` 는 프로세스 cwd 이므로 임시 디렉터리에서 시험하려면 명시적으로 지정해야 하고, 그러지 않으면 `path_not_allowed` 로 거절된다.

이것은 버그인지 설계인지 판단하지 않고 **사실로만 기록했다.** 기본값이 cwd 를 허용 경로로 삼는 것은 의도된 보안 설계로 보이므로 바꾸지 않았다.

## 재현 방법

프로브는 저장소에 포함하지 않는다(일회성 측정 도구). 이 문서의 수치를 다시 확인하려면:

1. **A-1** — 외부 팩 하나에 `noise: /^(a+)+b$/` 를 넣고 40자 `a` 로 호출. 종료되지 않으면 재현된 것이다.
2. **A-2** — `output_redaction_enabled: true` 로 두고 합성 비밀 5종을 `echo` 로 넘긴다. 하나라도 그대로 나오면 재현된 것이다.
3. **A-3** — `toCompact(["a|b","c"])` 를 본다. `"a|b|c"` 로 나오면 재현된 것이다.
4. **A-5** — `kubectl get pods` 에서 RESTARTS 가 0 이 아닌 프로세스를 본다. `(5d ago)` 가 Age 로 새면 재현된 것이다.
5. **A-6** — 개행·따옴표·탭 파일 이름이 있는 저장소에서 `git status --porcelain` 을 `-z` 없이 돌린다. 항목이 1개로 합쳐지면 재현된 것이다.
6. **B 부록** — 각 항목의 "재현 시도" 를 그대로 실행한다. **여전히 재현되지 않으면 그것도 정답이다.**

**재현되지 않은 것을 고쳤다고 보고하지 않는다. 재현된 것만 고친다.**
