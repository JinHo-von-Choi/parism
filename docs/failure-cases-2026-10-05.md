# parism 실패사례 — 실측으로 잡은 결함과 재현되지 않은 주장

작성자: 최진호
작성일: 2026-10-05

이 문서는 **실측으로 확인한 결함**과 **재현하지 못한 채 손대지 않은 주장**을 함께 둔다. 두 번째 부류가 이 문서의 더 중요한 절반이다. 계획을 읽고 고쳐도 되지만, **재현하지 못한 것을 고쳤다고 말하면 그것은 측정값이 아니라 추측이다.**

모든 수치는 이 호스트(Linux 6.8, Node 24.15, `@nerdvana/parism` 2.0.2 기준선)에서 측정했다.

---

## 부록 A. 재현해서 고친 결함

### A-1. 외부 팩 계약 정규식이 메인 스레드에서 실행됨 (서버 정지 위험)

**증상.** 외부 ParserPack 하나를 등록한 뒤 그 팩이 다루는 명령을 호출하면, 워커 시간 상한(기본 500ms)이 **90초 넘게** 무시된다. 프로세스가 `EXIT=124` 로 타임아웃되어 죽는다. 서버 스레드가 멈추므로 다른 요청도 함께 멈춘다.

**재현 입력.** 팩 계약에 `noise: /^(a+)+b$/`. 40자 `a` 를 `echo` 로 넘긴다.

**원인.** 워커가 팩 모듈을 격리 실행해 계약 선언을 넘기면서, 정규식(`noise`·`rowLine`·`acceptedValues`)을 **`RegExp` 객체 그대로** 직렬화해 메인 스레드에 보냈다. 메인 스레드가 그것을 실행했다. 팩이 선언한 재귀 역추적 패턴은 워커 안에서는 시간 상한에 걸려 멈추지만, **메인 스레드에서는 시간 상한의 통제를 받지 않는다.**

**수정.** 계약 정규식 평가를 워커 안으로 옮겼다. 워커가 원문 줄 분류(`dataLines`·`rowLines`)와 플래그 값 판정(`valueVerdicts`)을 수행하고 **개수와 참/거짓만** 돌려준다. 메인 스레드는 서술자 `{ __parism_regex__: { source, flags } }`만 받고 `RegExp` 를 만들지 않는다. 판정 결과가 없으면 형식을 거절한다 — 검증 없는 통과를 막는다.

**실측 전후.**

| | 수정 전 | 수정 후 |
|---|---|---|
| 40자 입력 호출 | 90초+ (종료 안 됨) | 시간 상한에 걸려 `parser_exception` |
| 전체 호출 합계 | 종료 불가 | 1.5초 |
| 메인 스레드 다른 요청 응답 | 멈춤 | 0.99ms |

**회귀 시험.** `tests/parsers/external-isolation.test.ts` — catastrophic backtracking 정규식이 있어도 호출 하나는 시간 상한 안에 끝난다.

### A-2. 리댁션을 켰는데 기본 패턴이 전혀 적용되지 않음 (비밀 유출)

**증상.** `guard.secrets.output_redaction_enabled: true` 로 켰는데 합성 비밀 5종이 **전량 그대로 반환**된다.

| 합성 입력 | 기대 | 실제 |
|---|---|---|
| `sk-` + 32자 | `[REDACTED]` | `sk-aaaa…` (그대로) |
| `ghp_` + 30자 | `[REDACTED]` | 그대로 |
| `AKIA` + 16자 | `[REDACTED]` | 그대로 |
| `xoxb-` + 10자 | `[REDACTED]` | 그대로 |
| `glpat-` + 20자 | `[REDACTED]` | 그대로 |

**원인.** 설정 로더가 `guard.secrets.output_patterns` 의 **기본값을 `[]`** 로 두었다. 사용자가 키를 생략하면 "값이 없다"가 아니라 "의도적으로 비활성"이 되어 기본 패턴 7개가 아예 쓰이지 않았다. SPECIFICATION이 원래 문서화하던 계약("`undefined` 이면 7개 DEFAULT 패턴, `[]` 이면 레덕션 비활성")에 코드가 맞지 않았다.

**수정.** 기본값을 두지 않게 바꿨다. 생략하면 기본 패턴을 쓰고, `[]` 를 명시하면 의도적 비활화로 구별된다.

**부수 발견 (같은 원인).** `mergeGuardConfig` 가 `secrets` 를 하위 키로 병합하지 않아, `output_redaction_enabled` 하나만 켜면 `secrets` 객체가 통째로 갈아끼워져 `env_patterns` 기본값 6개가 사라졌다. **자식 프로세스 환경 변수 시크릿 제거가 통째로 꺼졌다.** `secrets` 도 하위 키로 병합하도록 바꿨다.

**주의.** 이 수정은 **breaking change** 다. 이전에 키를 생략하고 리댁션을 켠 사용자는 실제로 가려지지 않은 값을 보고 있었다. 되돌리려면 설정에 `output_patterns: []` 을 명시해야 한다.

### A-3. compact 가 값을 조용히 잃음 (세 가지)

**증상 1 — 구분자 평탄화.** 중첩 배열을 구분자 문자열로 이어 붙여 `["a|b","c"]` 와 `["a","b","c"]` 가 **모두** `"a|b|c"` 가 되었다. 복원 불가다.

**증상 2 — 값이 섞인 배열의 타입 소실.** 배열 안의 `null` 은 문자열 `"null"` 이 되고 객체는 `"[object Object]"` 가 되었다. 그리고 **객체 뒤에 `null` 이 섞인 행 배열**(예: 49개 객체 + `null`)에서 `TypeError: Cannot read properties of null` 로 프로세스가 죽었다. 순환 참조와 `BigInt` 값도 `TypeError` 였다. 헤더가 하는 포맷 변환 하나가 실행 전체를 중단시킬 수 있었다.

**증상 3 — 첫 항목만 보고 형식을 결정.** `[{a:1},"str"]` 에서 두 번째 행이 `[null]` 이 되어 조용히 사라졌다.

**수정.** `src/parsers/compact.ts` 를 전(total) 함수로 다시 썼다. `CompactOutcome`(`{ok:true,value}` \| `{ok:false,reason,message}`)을 돌리고,
- 값이 섞인 배열은 **압축하지 않고** 그대로 둔다.
- 모든 행의 유형을 확인한 뒤 섞여 있으면 압축하지 않는다.
- 순환 참조·`BigInt`·깊이 64 초과는 `representation_not_lossless` 로 **실패로 보고한다.**

엔진은 그 경우 압축을 적용하지 않고 **원형 JSON 과 `stdout.raw` 를 모두 남긴다.** `failure = { kind: "parse", reason: "representation_not_lossless" }`.

**이것은 breaking change 다.** `toCompact()` 는 `unknown` 대신 `CompactOutcome` 을 돌린다.

### A-4. `find`/`du` 가 파일명 끝 공백을 지움

**증상.** 줄 구분자로 나눈 뒤 경로에 `trim()` 을 적용했다. `report ` 가 `report` 로, `dir /inner  ` 가 `dir /inner` 로 바뀌었다. **다른 경로로 오인될 수 있는 손실**이다.

`find -print0` 경로는 원래 정확했으나 줄바꿈 경로가 아니었다. **같은 파일이 출력 방식에 따라 다른 값을 냈다.**

**수정.** 두 경로에서 `trim()` 을 제거했다.

### A-5. `kubectl get pods` 의 RESTARTS 열 밀림

**증상.** 재시작 횟수가 0이 아니면 kubectl 이 `2 (5d ago)` 처럼 괄호 표기를 RESTARTS 뒤에 붙인다. 이를 한 열로 세어 다음처럼 읽었다.

```
age: "(5d"   ip: "ago)"   node: "8d"
```

**수정.** 닫는 괄호까지를 RESTARTS 값으로 묶고 그 다음 칸을 AGE 로 읽으며, 괄호 표기를 `last_restart` 로도 보존한다.

### A-6. `git status --porcelain` 에 `-z` 없이 주면 모든 항목이 하나로 뭉침 (**M1 이 만든 회귀**)

**증상.** M1 에서 `--porcelain` 을 NUL 레코드 전용 파서로 보냈다. 그런데 `-z` **없이** 주면 출력은 줄 구분 + C 이스케이프 + 따옴표 형식이다. 파서는 원문 전체를 한 레코드로 읽었다.

**실측 원문** (개행·따옴표·탭·화살표가 든 파일 이름 저장소).

```
 M mod.txt
R  old.txt -> new.txt
?? "arrow -> x.txt"
?? "line\nbreak.txt"
?? "quote\"dq.txt"
?? "tab\there.txt"
```

**수정 전 결과: 항목 1개.**

```json
{ "xy": "RM", "index": "R", "worktree": "M",
  "path": "keep.txt -> renamed.txt\n?? \"line\\nbreak.txt\"\n?? ... 전부" }
```

7개 항목이 1개로 합쳐지고 `path` 에 개행과 ` -> ` 표기가 그대로 남았다. **조용히 틀린 값**이다 — 실패도 아니고 경고도 없다.

**수정.** `-z`/`--null` 유무로 판별해 세 가지를 나눠 처리한다.

| | `-z` 없음(줄 모드) | `-z` 있음(NUL 레코드) |
|---|---|---|
| 레코드 경계 | 개행 | NUL |
| 경로 해석 | C 이스케이프 해제 | 가공 없음 |
| 이름 변경 | 한 줄의 `원래 -> 새` | **새 경로가 먼저**, 원래 경로가 다음 레코드 |

화살표는 **오른쪽에서** 찾는다 — 경로 자체에 `' -> '` 가 들어갈 수 있기 때문이다. 줄 모드에서만 항목에 `quoted: true` 를 붙여 **출력이 가공되었음을 값으로 밝힌다.** 두 형식의 `path` 값은 같아야 한다(원래 파일 이름).

**수정 후 실측.**

| | `-z` | 줄 모드 |
|---|---|---|
| 항목 수 | 6 | 6 |
| 경로 집합 | 동일 | 동일 |
| 근거 바이트 구간 | 25개 전부 원문 정확 | 25개 전부 원문 정확 |
| 빠진 근거 포인터 | 0 | 0 |

**이 수정이 두 번 만에 틀린 값을 냈다는 점이 중요하다.** 첫 수정은 rename 항목이 통째로 사라졌다(`readPath` 가 끝 경계를 몰라 `원래 -> 새` 의 왼쪽 경로를 통째로 읽었다). 두 번째 수정이 고쳤다. 프로브가 매번 실제 저장소로 원문 대조를 하지 않았으면 놓쳤을 것이다.

**회귀 시험.** `tests/parsers/git-status-porcelain.test.ts` — 10건 추가(줄 모드 파싱, 이스케이프 해제, 화살표 안 잘림, 두 형식 경로 집합 일치, 근거 바이트 대조, `-z` 여부가 경계를 정함).

### A-7. 토큰 예산이 행 수에 대해 이차로 늘었다 (**M2 가 만든 회귀**)

**증상.** 2,000행짜리 결과에 예산을 걸면 한 번에 **7.9초**가 걸렸다. 파일을 두 배로 하면 네 배가 되어 이차임을 눈으로 확인할 수 있었다. 벽시계 7,959ms, 반면 parism 이 스스로 재는 `total_ms` 는 **28.9ms**였다 — 계측 구간 밖에서 시간을 쓰고 있다는 뜻이다.

**CPU 프로파일로 지목을 좁혔다.** 95.1% 가 토큰 계측(`countTokens` 57.7%, `countJsonTokens` 18.2%, 이를 부르는 `measure` 19.2%)이었다. 계산이 무거운 게 아니라 **계측을 너무 많이 하고 있었다**는 뜻이다.

**계측 횟수를 직접 세어 원인을 확정했다.** `dist` 에 임시 카운터를 넣어 실행한 결과 2,000행에서 **2,012회**였다. 로그 탐색으로는 11회면 충분하다.

**원인.** `src/engine/budget/index.ts` 의 이분 탐색이 답(`lo`)을 구하고도 **그 결과를 버렸다.** 탐색이 끝난 뒤 재검증 루프가 `kept`(전체 행)에서 **한 행씩** 덜면서 매번 payload 전체를 다시 쟀던 것이다. O(n log n) 이 O(n²) 으로 무너졌다.

| 행 수 | 수정 전 | 수정 후 |
|---|---|---|
| 250 | 105ms | 33ms |
| 1,000 | 2,025ms | 47ms |
| 2,000 | 7,959ms | 67ms |
| 4,000 | (측정 안 함) | 182ms |

**답은 같았다.** 탐색 결과를 쓰면 재검증 루프는 표면이 늘어난 만큼 몇 행만 더 덜면 끝난다. 끝값은 이전과 동일하다 — 비용만 줄었다. 전 시험 1,399건이 그대로 통과했다.

**회귀 시험.** `tests/engine/budget.test.ts` — 시간을 재지 않고 **계측 호출 횟수**를 센다(시간은 CPU 상태에 흔들려 근거가 되지 않는다). 결함을 되살려 시험이 실제로 잡는지 확인했다: 수정 전 1,948회 → 100회 미만이어야 통과.

### A-8. 근거 구간 변환이 포인터마다 원문 전체를 다시 훑었다 (**M1 가 만든 회귀**)

**증상.** 1MB `git status` fixture 에 근거+보관을 켜면 **1,937ms**. 그런데 근거만 켜면 149ms, 보관만 켜면 93ms였다. 합이 아니라 **곱**이었다.

**조합을 나눠 원인을 찾았다.** 근거·예산·보관을 각각, 그리고 짝지어, 셋까지 재 봤다. `evidence + retain` 만 1,937ms 로 튀었다. 근거도 없이 보관만 하는 것보다 20배 비싸다는 뜻이다.

**원인.** `src/engine/review.ts` 의 `evidenceToByteSpans` 에서 줄 시작 위치 표를 **포인터마다** 다시 만들고 있었다.

```ts
for (const [pointer, spans] of Object.entries(raw)) {
  const lineOffsets = lineCharOffsets(unmasked);   // ← 반복문 안
```

`unmasked` 는 반복 안에서 한 번도 바뀌지 않는다. O(포인터 × 원문 길이) 이었다. 5천 행 × 4 필드 = 약 2만 포인터에 1MB 원문 — 200억 문자 연산.

**수정.** 반복문 밖으로 끌어올렸다. 1,937ms → **322ms(6배)**, on 전체 1,227ms → **487ms**.

**추측하지 않고 확인한 것.** 코드를 처음 읽었을 때 `line=0` 이 `toByteSpan` 에서 `null` 이 되어 근거가 전부 버려진다고 판단했다. **틀렸다** — `evidenceToByteSpans` 는 `line === 0` 을 "원문 전체 기준 절대 위치"로 따로 처리한다. 실제로 `explain_result` 로 확인해 보니 `source_kind: "verbatim"`, 바이트 구간 `3–13` 이 정확히 나왔다. 추측만으로 보고했다면 존재하지 않는 결함을 적었을 것이다.

**부수 발견 — 죽은 코드.** `toFieldEvidence` 와 `toByteSpan` 은 어느 곳에서도 호출되지 않는 죽은 코드였다(`toFieldEvidence` 는 `line=0` 도 처리하지 못했다). 제거했다.

**회귀 시험.** `tests/engine/evidence.test.ts` 2건 — 근거가 사라지지 않는지, 같은 원문에서 같은 근거가 나오는지.

### A-9. 저장소가 기록한 크기가 실제 보관본의 2.6배를 과소했다 (**M1 이 만든 계약 위반**)

**증상.** 성능 게이트 표에서 1MB `git status` 결과가 보관 한도(결과당 2MiB) 초과로 거절되는 걸 봤다. 그런데 그 숫자가 어디서 오는지 보니, 엔진이 저장소에 건네는 `bytes` 가 **원문과 본문만** 세고 있었다. **근거 맵을 아예 세지 않았다.**

근거 맵은 값 자체를 함께 담는다 — 근거가 그 값을 증명해야 하므로. 그래서 본문만큼이나, 대개는 더 크게 된다.

**실측 (500행).**

| | 기록한 bytes | 실제 보관본 | 비율 |
|---|---|---|---|
| 수정 전 | 246,158 B (0.23 MiB) | 635,224 B (0.61 MiB) | **2.58배 과소** |
| 수정 후 | 2,148,313 B (2.05 MiB) | — | 1.09배 |

**이것이 수치 문제가 아니라 계약 위반이었다.** 3,200행 `git status` 결과가 수정 전에는 1,654,421 B(1.58 MiB, 한도 2MiB 안)로 기록되어 `retained=true` 로 보관됐다. 실제 점유는 **4,308,313 B — 한도의 두 배**였다. `retained` 가 거짓말을 한 것이고, SPECIFICATION 5.2.0 의 "결과당 2MiB, 합계 32MiB" 는 실제로 그 2.6배까지 들어가는 상태로 집행되고 있었다.

수정 후 같은 입력은 올바르게 `retained=false` 로 거절된다. 수정 전후를 직접 되돌려 확인했다.

**한도를 세는 비용이 한도를 넘게 만들지 않게 했다.** 근거를 항목 하나씩 직렬화해 누적하고, **상한을 넘으면 즉시 멈춘다.** 이미 "거절"이라는 결론이 났으므로 그 이상 정확한 값은 쓸 곳이 없다. 이 조기 종료가 없으면 한도를 초과할수록 버릴 결과를 끝까지 재게 되어, 한도를 정한 것 자체가 비용이 된다.

**남는 1.09배는 `review` 와 지문 같은 고정 크기 구성요소다.** 세지 않았다 — 크기가 고정이고 한도 판단에 영향을 주지 않는다. 어느 정도인지 시험으로 고정했다(기록값이 실제 본문·근거의 80% 미만이면 실패).

**회귀 시험.** `tests/engine/evidence.test.ts` 2건 — 근거를 켜면 기록 크기가 커지는지, 기록값이 실제 직렬화 크기의 80% 이상인지. 결함을 되살려 시험이 실제로 잡는 것을 확인했다(221,326 < 918,015 로 실패).

**성능 게이트가 계약 위반까지 찾아냈다는 점이 중요하다.** 시간 표를 만들던 일이 저장소 한도가 2.6배 느슨다는 사실을 끌어냈다. 수치 표 없이는 이 사실을 알 방법이 없었다.

### A-10. 따옴표 안의 경로를 UTF-16 코드 단위로 읽어 이모지가 깨졌다

**증상.** 줄 모드 `git status --porcelain` 에서 이모지가 든 파일 이름이 원문과 다르게 나온다.

```
?? "emoji-😀.ts"   →   path = "emoji-��.ts"
```

**원인.** `readQuotedToken` 이 따옴표 안의 문자를 `text[i]` 로 한 글자씩 꺼내 `Buffer.from(ch, "utf8")` 로 인코딩했다. `text[i]` 는 UTF-16 **코드 단위**다. 이모지는 서로게이트 쌍이라 코드 단위 **두 개**이므로, 각각을 따로 인코딩하면 둘 다 U+FFFD 가 된다.

**왜 한글이 멀쩡했나.** BMP 문자(한글·일본어·맞춤)는 코드 단위 하나가 곧 코드 포인트라 드러나지 않는다. **BMP 만 통과하는 시험은 이 결함을 놓친다.** 다른 필드도 마찬가지 — 값이 조용히 바뀌는데 성공으로 보이는 유형이다.

**수정.** `text.codePointAt(i)` + `String.fromCodePoint` 로 읽고 `i += char.length` 만큼 이동한다.

**실측 재현 (실제 `git` 출력).** `git init` 후 이모지 파일을 두고 `git status --porcelain` 을 돌려 얻은 원문을 그대로 쓴다.

| 원문 | 파싱 결과 |
|---|---|
| `?? "emoji-😀.ts"` | `emoji-😀.ts` |
| `?? "a-😀-b-😀-c.txt"` | `a-😀-b-😀-c.txt` |
| `?? "한글-😀-mixed-🚀.txt"` | `한글-😀-mixed-🚀.txt` |
| `?? "quo\\"te-😀.txt"` | `quo"te-😀.txt` |

8진 바이트 이스케이프(`"n\\303\\251w.txt"` → `néw.txt`)와 개행·탭·역슬래시 이스케이프는 계속 정상이다. **미인식 이스케이프(`\\q`)는 `undefined` 로 거절한다** — 되돌릴 수 없는 값임을 아는 쪽이 옳다.

**회귀 시험.** `tests/parsers/git-status-porcelain.test.ts` 8건. 결함을 되살려 확인했다(5건 실패).

### A-11. 줄 모드 이름 변경에서 화살표를 경로 안에서 찾아 경로를 잘라냈다

**증상.** 줄 모드 `git status --porcelain` 의 이름 변경에서, **새 경로에 ` -> ` 가 들어 있으면** 경로가 잘리고 닫는 따옴표가 값에 남는다. 오류도 나지 않는다.

```
원문 : R  "arrow -> here.txt" -> "new -> name.txt"
결과 : path = "name.txt"        ← 기대 "new -> name.txt"
       orig_path = "arrow -> here.txt"   ← 이쪽은 맞았다
```

**원인.** `rest.lastIndexOf(" -> ")` 로 구분자를 찾았다. 이 원문에서 " -> " 는 **세 번** 나오고, 마지막 위치는 **새 경로의 따옴표 안쪽**이다. 그 위치에서 잘라 오른쪽을 읽으니까 `name.txt"` 가 나왔다.

**이건 실제 git 출력이다.** 손으로 만든 입력이 아니다. 실제 `git mv "arrow -> here.txt" "new -> name.txt"` 후 `git status --porcelain` 을 돌려 얻은 줄을 그대로 복사했다. git 은 공백이 든 경로를 **항상** 따옴표로 감싸 출력하므로(실측: `A  "a b.txt"`), 이런 화살표가 경로 **안쪽**에 들어가면 반드시 인용된다.

**수정.** `lastArrowOutsideQuotes` — 따옴표 상태를 따라가며 **바깥의** 화살표만 센다. 구분자는 구조상 항상 따옴호 밖에 있다.

**왜 `-z` 모드는 멀쩡했나.** `-z` 는 경로를 가공하지 않고 NUL 로만 나누므로 화살표 구분이 필요 없다. **두 모드를 나눠 검사하지 않으면 한쪽의 결함이 다른 쪽에서 가려진다.**

**회귀 시험.** 6건. 결함을 되살려 확인했다(2건 실패).

**같이 고친 것 — 지어내던 값.** `-z` 모드에서 이름 변경의 짝 레코드가 비어 있으면 `orig_path: ""` 가 붙었다. 실제 git 은 그런 출력을 내지 않지만, 넣으면 **빈 문자열이 지어낸 원래 경로**가 된다. 모른다 하면 없는 것이지 빈 문자열이 아니다. 빈 레코드는 짝으로 받지 않는다.

### A-12. 따옴표로 감싸진 경로는 근거 검증을 통과하지 못했다 (고쳤다)

**결함이었다.** 값을 지어내지는 않지만 **증명할 수 있는 근거를 버렸다** — M1 의 핵심 가치가 그대로인데 근거만 떨어지는 상태였다.

**실측.** `verifySpans` 로 `/entries/0/path` 근거를 대조했다.

| 원문 | 구간이 담는 것 | transform | 수정 전 | 수정 후 |
|---|---|---|---|---|
| `?? plain.ts` | `plain.ts` | — | 통과 | 통과 |
| `?? "with space.ts"` | `"with space.ts"` (따옴표 포함) | `unescape_c_quotes` | **실패** | 통과 |
| `?? "이름-한글.ts"` | `"이름-한글.ts"` | `unescape_c_quotes` | **실패** | 통과 |
| `?? "emoji-😀.ts"` | `"emoji-😀.ts"` | `unescape_c_quotes` | **실패** | 통과 |
| `?? "line\nbreak.txt"` | `"line\nbreak.txt"` | `unescape_c_quotes` | **실패** | 통과 |

**원인.** 문자열 대조가 `text.slice(start, end) === value` 였다. **transform 을 고려하지 않았다.** 그런데 구간은 인코딩된 표기를 가리키므로, 원문이 `"with space.ts"` 면 그 안에서 `with space.ts` 를 그대로 찾을 수 없다.

**효과.** 정확성 게이트 1,200 케이스에서 `source_kind: "none"` 으로 낮아진 구간이 **8,819건**이었다. 수정 후 **0건**이다(아래 A-15·A-16 수정까지 합친 결과).

**수정 — transform 별 역변환.** `verifySpans` 가 구간이 **선언한** 변환의 역변환을 알고 정확히 같을 때만 통과시킨다.

**느슨해지는 방향이 아니다.** 세 가지를 지킨다.
1. **인코딩을 가리키는 transform 만 넣는다.** `trim`·`strip_tree_prefix` 는 넣지 않는다 — 그 구간은 이미 다듬어진 값을 가리키므로 역변환을 해도 바뀌는 것이 없다. 넣으면 여분의 공백이 붙은 구간까지 근거로 받아들인다.
2. **정확히 같을 때만 통과한다.** 부분 일치도 정규화도 허용하지 않는다.
3. **모르는 변환은 통과시키지 않는다.** 역변환을 모르는 변환을 관대하게 대조하면 근거를 지어내는 쪽으로 기운다. 모른다고 말하는 편이 낫다.

**계층 역전은 만들지 않았다.** 역변환이 필요하므로 `engine` 이 `parsers` 를 알아야 한다고 판단했다. 그런데 역전시키지 않고도 같은 결과를 낼 수 있었다 — C 이스케이프 코덱은 **의존이 하나도 없는 순수 텍스트 변환**이므로 `src/engine/c-quotes.ts` 로 빼고, **파서가 엔진에서 가져가게** 했다. 파서는 이미 엔진에 의존하므로(`engine/evidence.js`) 반대 방향이 자연스럽다. `src/parsers/git/paths.ts` 는 이름만 유지한 재내보내기로 남겼다.

**회귀 시험.** `tests/engine/evidence-mapping.test.ts` 4건 (역변환 표를 지워 2건 실패).

### A-15. 근거 구간(바이트)을 문자 인덱스로 잘라, 비 ASCII 이후가 전부 어긋났다

**결함이었다.** M1 의 근거 기능이 **비 ASCII 가 있는 출력에서 조용히 무너졌다.**

**원인.** `evidenceToByteSpans` 는 근거 구간을 문자 위치에서 **바이트 위치로** 바꾼다(맞다 — 근거는 사람이 원문에서 바이트로 짚는 것이다). 그런데 `verifySpans` 는 그 바이트를 **문자열 인덱스로** 잘랐다. 원문에 비 ASCII 가 한 글이라도 있으면 바이트 위치와 문자 위치가 다르다.

**실측 — 실제 git 저장소.** `cfg.json` · `emoji-😀.ts` · `plain.ts` · `이름-한글.ts` 가 있는 저장소에서:

| 경로 | 수정 전 | 수정 후 |
|---|---|---|
| `cfg.json` | `verbatim` | `verbatim` |
| `emoji-😀.ts` | **`none`** | `verbatim` |
| `plain.ts` | **`none`** | `verbatim` |
| `이름-한글.ts` | **`none`** | `verbatim` |

**`plain.ts` 가 깨졌다**는 점이 중요하다. 그 파일은 순수 아스키다. **앞에 이모지가 한 글만 있어도 뒤의 모든 근거가 망가지므로, "이 출력은 아스키여서 괜찮다" 는 보장도 되지 않는다.** 원문 바이트 61, 문자 51 — 10글자의 차이가 뒤를 전부 밀었다.

**영향 범위.** `explain_result` 의 `quoted`(사용자에게 보여주는 근거 원문 조각)도 같은 문자 인덱스 절단을 쓰고 있었다. 근거가 어긋나면 사람이 확인하는 문자열도 같이 어긋난다.

**수정.** `sliceByBytes` — 바이트 오프셋을 문자 인덱스로 되돌린 뒤 자른다. 순수 아스키면 표를 만들지 않는다(대부분의 출력이 이 경로다). 표는 **마지막 원문 하나만** 기억한다 — 엔진은 한 결과를 만들 때 같은 원문으로 포인터를 전부 돌기 때문이다.

**실측 (함수를 만들며내가 한 실수).** 처음에 경계 표를 `table[0] = 1` 처럼 **앞 문자까지 덮어쓰도록** 써서, 표가 있는 출력은 아스키 출력까지 함께 망가졌다(불필요한 저하 8,392 → 12,483). 자기 구간만 채워야 한다.

**회귀 시험.** `tests/engine/evidence-mapping.test.ts` 3건 (되살리면 1건 실패).

### A-16. 마스킹 구간을 잘못된 좌표계로 옮겨, 뒤쪽 근거를 삼켰다

**결함이었다.** 셋 중 가장 조용했다. **값이 틀린 게 아니라 근거가 없는 값**이라 아무도 몰랐다.

**원인 — 두 가지가 함께.** `maskWithRanges` 는 패턴을 순서대로 적용하면서 뒤 단계에서 발견한 구간을 최초 좌표계로 되돌린다. 거기서
1. **같은 단계의 구간에도 앞 구간의 길이 감소를 적용**했다. 같은 단계의 구간들은 치환 **전의 같은 문자열**에서 나온 것이라 좌표계가 같다. 적용하면 구간이 앞당겨진다.
2. **부호가 반대**였다. 치환은 문자를 줄였으니 최초 좌표에서는 **더 뒤**에 있다. 빼면 앞당겨진다.

**실측 — 시크릿 두 개가 있는 출력.**

| | 값 |
|---|---|
| 참 구간 | `[282, 324)` — `ghp_CANARY…` 42글자 |
| 잘못된 값 | `[250, 292)` — **32글자 앞당겨짐** |

앞당겨진 구간이 삼킨 것은 `zzz…zzz.ts` 의 끝, 개행, **다음 레코드의 상태 두 글자**였다. 그래서 그 레코드의 `xy` 근거가 **경로 한가운데 10바이트**를 가리켰다. 원문에는 그 자리에 `zzz` 가 있었다.

**왜 아무도 몰랐나.** 근거가 없는 값이라 검증이 실패했을 뿐 **거부되지는 않았다.** 그 레코드는 경로 값이 정상이라 사용자는 아무 이상을 느끼지 못했다. 근거를 조회해야 드러나는 종류다.

**수정.** 구간마다 발견된 단계 번호를 함께 기억하고, **같은 문자열에서 나온 구간끼리는 이동시키지 않는다.** 앞선 단계의 구간과 비교할 때는 그 구간을 현재 단계 좌표로 되돌린다.

**회귀 시험.** `tests/engine/evidence-mapping.test.ts` 3건 (되살리면 2건 실패).

### 게이트 지표도 함께 바로잡았다

마스킹으로 가려진 값은 **검증할 수 있는 것이 아니다** — 시크릿이 `[REDACTED]` 로 바뀌었으니 물리적으로 같을 수 없다. 엔진은 이런 구간을 `masked` 로 따로 보고하므로 **옳은 처리**다. 그런데 게이트는 그것을 '검증 실패' 로 세어, 마스킹이 근거를 약화시키지 않는데도 약화시키는 것처럼 세고 있었다.

갈라 세도록 바꾼 뒤의 최종 실측(1,200 케이스):

| | 건수 |
|---|---|
| 다섯 가지 판정 위반 | **0** |
| 그 밖에 못 담은 구간 | **0** |
| 가려져서 담을 수 없는 구간 | 177 (옳은 처리) |

**총합만 세지 않는 것이 중요하다.** 어느 transform·어느 필드에서 남았는지 알지 못하면 그 숫자가 무엇을 말하는지 모른다. 포인터와 transform 별로 갈라 세도록 했고, 그래서 위 두 결함(A-15·A-16)이 **이 지표를 통해 드러났다.**

### A-13. `parism eval` 이 help 에는 있는데 실행되지 않았다 — 조용히 MCP 서버가 되었다

**이건 계획서가 이름 그대로 짚은 항목이다.** 4.5장: *"parism eval 진입점 누락을 고치고 결과 판정을 execution/parse/task로 분리한다."* 진입점은 있으나 **argv 라우팅이 빠져 있었다.**

**증상.** `parism eval` 은 아무것도 하지 않는다.

```
$ parism eval parse-error --verbose
(출력 없음)   exit 0   0.42초
```

사용자에게는 **성공한 것처럼 보인다.** exit 0 이다.

**원인.** `commander` 에 등록한 명령과 `process.argv[2]` 를 **실제로 라우팅하는 목록**이 따로 관리되고 있었고, 앞에만 `eval` 이 있었다(`src/index.ts` 의 `CLI_COMMANDS`). 그래서 `parism eval …` 은 CLI 경로를 타지 않고 **MCP 서버를 띄웠다.** 표준 입력이 JSON-RPC 줄을 기다리며 멈춘다.

**증거를 세 갈래로 잡았다.** "안 돌아간 것" 과 "다른 게 돈다" 를 구분해야 한다.

| 관측 | 결과 | 뜻 |
|---|---|---|
| `node dist/index.js eval parse-error` | 출력 0바이트, exit 0, 0.42초 | 아무 일도 하지 않음 |
| 같은 명령에 **stdin 을 열어두면** | **종료하지 않음** (exit 124) | 평가가 아니라 **MCP 서버**가 떴음 |
| 같은 조건의 `inspect` | 즉시 exit 0 | CLI 경로는 정상 |

stdin 을 열어둔 채로 멈추는 것이 결정적이었다. 평가였다면 몇 초 안에 끝나야 한다.

**숨은 사실 두 가지.** 첫째, `--help` 에 `eval` 이 **정상적으로 광고되고 있었다** — help 는 거짓말을 했다. 둘째, 앞선 검토에서 "진입점은 존재하나…" 로만 적고 넘어갔었다. **도구가 있다는 것과 실행된다는 것은 다르다.** 그 차이는 이렇게 재현해야만 보였다.

**수정.** 라우팅을 `src/cli/routing.ts` 로 옮겨 단일 출처로 만들고 `eval` 을 넣었다. 그리고 **구조**를 막는 시험을 뒀다 — `commander` 에 등록된 모든 명령이 라우팅 대상인지 대조한다. 앞으로 명령을 추가하며 라우팅을 잊어도 시험이 먼저 깨진다. 결함을 되살려 확인했다(`eval` 을 목록에서 빼면 2건 실패).

### A-14. `parism eval` 이 서로 다른 세 가지를 한 비율에 섞었다 (계획서 4.5장)

**증상.** 예전 판정은 `result.ok` **한 개 boolean** 이었다. 그래서 아래 세 가지가 뒤섞였다.

- 이 호스트에 명령이 있는가
- parism 에 그 명령의 파서가 있는가
- 명령이 기대대로 끝났나

**실측으로 드러난 예 — `node --version` 이 실패로 집계됐다.** 실제로는 **가드가 정상적으로 막은 것**이었다(`command_not_allowed`). 명령이 안 돌았고 파싱도 없었고 과제도 없었는데, 보고서는 "완료율 85.7%" 의 실패 1건으로 적었다. **정책이 일한 것을 parism 의 실패로 센 것**이다.

**더 나쁜 것 — 시나리오가 호스트를 재고 있었다.** `retry-rate` 라 이름 붙은 시나리오가 `curl -I http://localhost:9999` · `docker ps` · `kubectl get pods` · `helm list` 를 돌렸다. 이 호스트에 클러스터가 있는지를 재는 것이지 parism 을 재는 것이 아니었다. **재시도를 한 번도 세지 않았다.**

**수정 — 세 층으로 분리했다.**

| 층 | 무엇을 보는가 |
|---|---|
| `execution` | 명령이 **실제로 실행되었는가.** 가드 거절과 실행 실패를 구분한다 |
| `parse` | 구조로 읽었는가 · 파서가 없는 것 · 명시적 파싱 실패를 구분한다 |
| `task` | 자기 과제를 해냈는가. **없는 것을 찾는 과제는 실패해야 성공이다** |

**기대값을 세우지 않은 항목은 비율에 넣지 않는다.** 모르면 안다고 적지 않는다. 호스트에 따라 달라지는 항목(`docker ps`)은 기대 없이 관측만 남긴다.

**`retry-rate` 는 이름이 하는 일을 이제 실제로 한다.** 계약은 하나 — *저장한 결과는 다시 실행하지 않는다.* 관측하려면 "다시 돌렸다면 값이 달라지는" 상황이 필요하다. 그래서 **빈 임시 저장소**에서 `git status --porcelain -z` 를 보관하고, 그 뒤에 **새 파일을 만든다.** 새 파일이 보이면 재실행이다. 관측이 추정에 의존하지 않는다 — 시간을 두는 방법보다 확실하다.

**이 검사 중 발견한 것 두 가지.**

1. **임시 저장소가 경로 가드에 막혔다.** 기본 `allowed_paths` 는 실행 디렉터리 하나다. 엔진은 실행 디렉터리를 인자로 받지 않고 설정 파일로 받으므로, 그 경로가 든 설정을 넘긴다. **이 사실을 몰랐으면 "계약 위반" 이 아니라 "가드에 막힘" 을 계약 위반으로 보고했을 것이다.**
2. **명령 거절과 경로 거절을 같은 `blocked` 로 뭉뚱그렸다.** `ls` 는 허용 목록에 **있는데** `/tmp` 가 밖이라 막힌 것이었다(`path_not_allowed`). 처음에는 이를 "parism 이 `ls` 를 못 실행한다" 고 읽었다. 구분하지 않으면 어느 쪽인지 알 수 없다.

**두 가지를 섞어 만든 오진도 하나.** `ls-missing` 항목이 "없는 파일 찾기"(task) 와 "형식 미지원"(parse) 을 한 항목에 실어, 서로 다른 두 실패가 하나처럼 보였다. 나눴다. 형식 미지원은 그 자체로 계약이다 — 계획서 4장 *"지원하지 않는 형식은 실패로 드러나야 한다."* `ls` 에 `-l` 이 없으면 파서는 `unsupported_format` 로 말하고 대체 인자를 제시한다(**빈 결과를 조용히 내지 않는다**).

**결과.**

```
── execution-parse ──
  층        기대있음  일치    관측
  execution      12   12/12    ran 11, blocked 2
  parse           3     3/3     parsed 10, parse_error 1
  task            2     2/2     succeeded 9, failed 2
── retry-rate ──
  task            2     2/2     succeeded 2
```

**회귀 시험.** `tests/cli/eval.test.ts` 5건 — 시나리오 구조(모든 항목에 기대가 있는지, id 중복, `retry-rate` 항목이 실제 명령이 아닌지, 모순된 기대가 없는지)를 고정한다. 호스트에 따라 달라지는 실제 실행은 여기서 판정하지 않는다.

## 부록 B. 재현하지 못해 손대지 않은 것

**이 부록이 더 중요하다.** 계획서나 이전 검토에 있던 주장을 **재현하지 못했다.** 그러니 고치지 않았고, 고쳤다고 말하지도 않는다.

### B-1. grep 콜론 포함 파일명 유실

**주장.** `grep` 출력이 `파일:내용` 형식이므로 파일 이름에 콜론이 있으면 필드가 어긋난다.

**재현 시도.** 콜론이 든 파일 이름으로 `grep -r` 실행.

**결과.** 재현되지 않았다. `unknown` — 이 호스트의 grep 버전·로케일·인자 조합에서 그런 출력을 만들지 못했다. **어느 버전에서 재현되는지는 모른다.** 손대지 않았다.

### B-2. `find -print0` 로 개행 든 파일 이름 유실

**주장.** `find` 가 `-print0` 을 주지 않으면 개행이 든 파일 이름에서 줄이 깨진다.

**재현 시도.** 개행·탭·따옴표가 든 파일 이름 저장소에서 비교.

**결과.** 이미 정확했다. `-print0` 경로는 원래 올바르게 동작했고, **어긋난 쪽은 줄바꿈 경로였다**(A-4). 주장이 방향을 잘못 짚었다. 줄바꿈 경로만 고쳤다.

### B-3. macOS `stat` UID

**주장.** `stat` 파서가 macOS 의 `Uid` 표현을 못 읽는다.

**결과.** 재현 불가 — 이 호스트는 Linux 다. **판단하지 못했다**(`unknown`). macOS 에서 검증하기 전까지 손대지 않는다.

### B-4. `_summary` 필드 충돌

**주장.** 파서가 내는 `_summary` 와 서버가 붙이는 `_summary` 가 충돌한다.

**결과.** 재현되지 않았다. 현재 코드 경로에서 충돌하는 조합을 찾지 못했다.

### B-5. `parism eval` 진입점 누락

**주장.** `parism eval` 명령이 없다.

**결과.** **진입점은 존재했다.** 다만 `retry-rate`/`completion` 시나리오 2개가 비고(footnote) 4/7로 가드 사유 때문에 실패했다. 진입점 부재라는 주장은 **틀렸다.** 시나리오 실패는 별개 문제로 기록만 한다.

## 부록 D. 이번 작업에서 실측이 잡은 내 결함

자기 검토다. 계획을 지켰다고 끝내지 않고, 실측이 코드의 결함을 드러낸 사례.

| 결함 | 어떻게 잡혔나 |
|---|---|
| 스테이징 안 됨(`" M src/a.ts"`)이 `RECORD` 정규식에서 거절됨 | M1 근거 대조 중 `" M src/a.ts"` 가 유실됨을 발견. 문자 클래스에 공백 추가 |
| `ps` 정규식의 `\\` 이스케이프 유실 | 근거 바이트 대조 중 원문과 불일치. 복원 |
| 숫자 근거 대조를 문자열로 함 | `"0.0"` 과 `0` 이 근거 불일치. 수치 비교로 수정 |
| **예산을 계산하고도 응답에 반영하지 않음** | M2 수용 기준①(final payload 상한)이 실패로 드러남. 표면만 붙고 본문은 그대로였음 |
| **본문만 재서 최종 payload 가 상한 초과** (measured 1481 > 1400) | 표면(누락 내역·진행 정보)을 붙인 뒤 최종 크기로 재야 한다는 사실을 실측이 알려줌. 전체 응답을 후보마다 재도록 변경 |
| `shrunkParsed` 내부 필드가 응답으로 새어나감 | 예산 경로 점검 중 발견. 제거 |
| **identity 미확정 행이 있는데 다른 쪽에 키가 안 보이면 `added` 로 단정** | M3 "거짓 삭제 0" 조건이 삭제 쪽에만 적용돼 있었음. presence 주장 보류(`canClaimPresence`)로 수정. 삭제 쪽도 동일 사유로 보류 |
| `--porcelain` non-`z` 항목 뭉침 (A-6) | tarball smoke test 의 2차 실행에서 발견 |

**"수용 기준을 정의해 두면 실측이 어긋난 자리를 알려준다"가 이 표의 요지다.** 위 여덟 건은 모두 내가 쓴 기준이 잡아낸 것이다.

## 부록 E. tarball 소비 smoke test 에서 나온 것

`npm pack` 한 tarball 을 클린 디렉터리에 설치하고 **설치본만** import 해서 12개 항목 31개 검사를 돌렸다. 전부 통과했다.

**발견 1 — 패키지 결함으로 단정하지 않은 것 (보고만).** `package.json` 의 `exports` 맵에 `./package.json` 과 `require` 조건이 없다. `require.resolve('@nerdvana/parism/package.json')` 이 막힌다. ESM 전용 패키지이므로 `require` 해석이 막히는 것은 **의도된 것**으로 보고, 소비자가 버전 확인을 위해 그 패턴을 쓰는 경우가 있다는 사실만 기록했다. exports 맵에 `./package.json` 을 열지는 **하지 않았다** — 스모크 스크립트를 우회하는 것으로 충분하고, 공개 계약을 늘리는 일은 이번 범위가 아니다.

**발견 2 — 사용 방식의 함정 (실측 사실).** `createEngine({ configPath })` 는 다층 설정 대신 `loadConfig` **단일 층**을 쓴다. 그래서 `PARISM_ALLOWED_PATHS` 같은 **환경변수 레이어가 반영되지 않는다.** 허용 경로를 설정 파일에 직접 적어야 한다. 기본 `allowed_paths` 는 프로세스 cwd 이므로 임시 디렉터리에서 시험하려면 명시적으로 지정해야 하고, 그러지 않으면 `path_not_allowed` 로 거절된다.

이것은 버그인지 설계인지 판단하지 않고 **사실로만 기록했다.** 기본값이 cwd 를 허용 경로로 삼는 것은 의도된 보안 설계로 보이므로 바꾸지 않았다.
