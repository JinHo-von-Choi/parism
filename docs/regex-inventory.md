# 정규식 계약 인벤토리

`@nerdvana/parism` 의 정규식 사용처를 전수 조사해, Rust `regex` 엔진으로 옮길 수 있는
것과 옮기면 안 되는 것을 분리한다. 이 문서는 3단계(Rust 정규식 전환)의 진입 게이트다.

- 작성일: 2026-10-22
- 대응 태스크: `plan/feature-environment-awareness-1.md` TASK-001, TASK-026, RISK-002
- 조사 기준 커밋: `cf6d086` (v2.1.1)

## 1. 결론

| 항목 | 값 |
|------|-----|
| `new RegExp(...)` 호출 지점 | 7곳 |
| 그중 사용자 입력에서 오는 패턴 | 3곳 (`redactor.ts` 2, `mask-map.ts` 1) + `sanitize.ts` 1곳(부분) |
| 정적 리터럴 정규식 | 181건 / 179개 소스 라인 (아래 2개 명령의 출력 합계) |
| lookaround 를 쓰는 정적 리터럴 | 5곳 |
| 역방향 참조(`\1` 등)를 쓰는 곳 | 0곳 |
| Rust 로 옮길 대상 (CON-005) | `redactor.ts` / `mask-map.ts` / `sanitize.ts` 의 **사용자 제공 패턴만** |

**판정**: 3단계에 들어가도 된다. 옮길 대상인 사용자 제공 패턴 세 경로에서
lookaround 와 역방향 참조를 쓰는 곳이 없고, 역추적 위험이 있는 정적 리터럴은
옮길 대상이 아니다. 다만 **유니코드 경계 의미 차이**가 남아 있고, 이는 6절에 적었다.

## 2. 조사 방법

재현 가능한 명령 두 개로 전수를 뽑았다.

```bash
# 동적 컴파일 전수
grep -rInE "new RegExp|RegExp\(" src --include='*.ts'

# 정적 리터럴 전수 (호출 인자 위치)
grep -rInEo "(match|replace|replaceAll|split|test|exec|search)\((/[^/]*/[gimsuy]*)" src --include='*.ts'

# 정적 리터럴 전수 (상수 선언 위치)
grep -rInEo "(const|let) [A-Za-z_]+(: [^=]+)? = (/[^/]*/[gimsuy]*)" src --include='*.ts'
```

두 정적 명령의 출력은 108건 + 73건 = 181건이다. 하나의 정규식이 상수로 정의돼
여러 번 쓰이면 **정의 위치 한 번만** 센다. `new RegExp(` 검색 결과 7건 중
`redactor.ts:19` 는 주석이므로 실제 호출은 6건이 아니고, **`redactor.ts` 의 26행과 43행
두 곳이 서로 다른 목적이므로 둘 다 센다**. 실제 호출 7곳의 전수는 4절에 있다.

**계획서 수치 정정**: 계획서 `CON-005` 는 정적 정규식을 "50여 개" 라고 적었으나
실측은 181건이다. 50여 개는 파서 파일 한 묶음만 센 값이었다. 전환 범위
(CON-005: 사용자 제공 패턴 3곳 한정)는 이 정정과 무관하게 그대로 유효하다.

## 3. 분류 기준

| 분류 | 뜻 | Rust 전환 대상 |
|------|-----|---------------|
| `사용자 제공` | 설정 파일이나 호출자가 준 문자열을 컴파일한다 | 예 |
| `정적 조합` | 코드가 정한 조각을 이어 붙여 만든다. 사용자 문자열이 들어가지 않는다 | 아니오 |
| `정적 리터럴` | 소스에 그대로 적힌 정규식 | 아니오 |

`CON-005` 는 `src/` 전체의 정적 정규식 181건을 옮기지 말라고 못박는다.
이유는 단순하다. 정적 리터럴은 개발자가 한 번만 검토한 것이고, 위험 패턴이 들어갔으면
코드 리뷰에서 걸린다. **사용자 제공 패턴**은 실행 시마다 임의의 문자열이 들어오므로
따로 다뤄야 한다.

## 4. `new RegExp(...)` 호출 7곳 전수

| # | 위치 | 분류 | 패턴 출처 | Rust 전환 |
|---|------|------|----------|----------|
| 1 | `src/engine/redactor.ts:26` | 사용자 제공 | `guard.secrets.output_patterns` 또는 `DEFAULT_OUTPUT_REDACT_PATTERNS` | 예 |
| 2 | `src/engine/redactor.ts:43` | 사용자 제공 | 같은 목록의 컴파일 검증 | 예 (검증 전용) |
| 3 | `src/engine/mask-map.ts:36` | 사용자 제공 | `resolveRedactPatterns(config)` 가 넘긴 목록 | 예 |
| 4 | `src/fixtures/sanitize.ts:89` | 혼합 | `rule.pattern` 이 문자열이면 `escapeRegExp` 결과(리터럴), `RegExp` 면 `.source` | 부분 (RegExp 분기만) |
| 5 | `src/parsers/fs/ls.ts:27` | 정적 조합 | `MTIME` 상수를 끼워 넣은 고정 형태 | 아니오 |
| 6 | `src/parsers/text/grep.ts:162` | 정적 조합 | grep 옵션 종류로만 바뀌는 구조 패턴. **사용자 패턴 문자열은 들어가지 않는다** | 아니오 |
| 7 | `src/parsers/text/wc.ts:66` | 정적 조합 | 열 개수로만 바뀌는 구조 패턴 | 아니오 |

4번의 `sanitize.ts` 는 주의가 필요하다. `SanitizeRule.pattern` 은 `string | RegExp` 이고,
- `string` 분기: `escapeRegExp()` 로 특수문자를 모두 이스케이프한다. 결과는 항상 리터럴이므로
  Rust 로 옮겨도 결과가 같다.
- `RegExp` 분기: `defaultRules()` 의 내장 규칙이거나 호출자가 준 `extraRules` 다.
  내장 규칙 3개는 5절에 적었다.

`grep.ts` 는 사용자가 준 패턴을 **정규식으로 바꾸지 않는다**. grep 자신이 매칭하고,
parism 은 출력 줄짜기를 파싱할 뿐이다. 그래서 `grep -E 'a{100000}{100000}'` 같은
패턴이 parism 을 스폰하게 만드는 일은 없다.

## 5. 옮길 대상 정규식의 실제 내용

### 5.1 기본 리댁션 패턴 (`src/engine/redactor.ts:7-15`)

```
sk-[A-Za-z0-9_-]{20,}
ghp_[A-Za-z0-9]{30,}
gho_[A-Za-z0-9]{30,}
glpat-[A-Za-z0-9_-]{20,}
AKIA[0-9A-Z]{16}
xox[baprs]-[A-Za-z0-9-]{10,}
Bearer\s+[A-Za-z0-9._-]+
```

모두 명시적 문자 클래스다. `\d` `\w` `\b` `\p{...}` 를 쓰지 않는다.
Rust `regex` 크레이트에서 그대로 컴파일된다.

### 5.2 fixture 새니타이즈 기본 규칙 (`src/fixtures/sanitize.ts:76-81`)

```
\b(?:gh[pousr]_[A-Za-z0-9]{16,}|glpat-[A-Za-z0-9\-_]{16,}|AKIA[0-9A-Z]{16}|xox[abposr]-[A-Za-z0-9-]{10,}|eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{5,})\b
\b(--?(?:token|password|passwd|secret|api[-_]?key|auth)(?:=|\s+))(\S+)
```

둘 다 `\b` 를 쓴다. Rust `regex` 에 `\b` 가 있어 컴파일은 된다. 다만 경계의 의미가
6절의 차이에 걸린다.

### 5.3 사용자 설정으로 들어오는 패턴

`guard.secrets.output_patterns` 는 설정 파일에 적힌 문자열을 그대로 쓴다.
**임의의 정규식 문법을 쓸 수 있다.** 여기서 lookaround 나 역방향 참조가 나올 수 있다.
`SEC-004` 의 폴백 규칙(TS 로 되돌리고 그 사실을 결과에 명시)이 필요한 이유가 이것이다.

## 6. Rust `regex` 크레이트로 옮길 때 남는 차이

컴파일은 된다는 것과 **같은 결과가 나온다는 것**은 다르다. 확인해야 할 차이 3가지.

| 차이 | JavaScript | Rust `regex` | 영향 |
|------|-----------|--------------|------|
| `\b` 경계 | `\w` = `[A-Za-z0-9_]` (ASCII 전용) | 유니코드 word 문자 기준 | 이웃 문자가 비ASCII 면 경계 위치가 달라진다. 예: `éghp_aaa...` 에서 JS 는 경계가 성립하고 Rust 는 성립하지 않는다 |
| `\d` `\w` `\s` | `\d` = `[0-9]`, `\w` = ASCII 만 | 유니코드 자리표 숫자/문자 포함 | 아랍 숫자 등 비ASCII 숫자를 `\d` 로 매칭하는 결과가 달라진다 |
| `$` 의미 | 문자열 끝에서만 | 문자열 끝에서만 (동일) | 차이 없음 |

현재 기본 패턴 3종은 `\d` `\w` 를 쓰지 않으므로 **5.1 은 그대로 이식된다**.
5.2 의 `\b` 두 개는 비ASCII 이웃이 붙은 입력에서 결과가 달라질 수 있다.

이 차이는 "사용자에게 보이는 결과가 바뀐다"는 뜻이다. `REQ-009` (fixture replay 바이트 동일성)를
만족시키려면 3단계에서 두 가지 중 하나를 고른다.

1. Rust 쪽에서 `\b` 대신 **ASCII 경계**를 명시적으로 쓴다. `\b` 대신 `(?-u:\b)` 로 유니코드 경계를 끄는 방법과,
   ASCII 만의 lookaround 없는 동등 표현을 쓰는 방법이 있다.
2. Rust 로 옮기지 않고 TS 로 남긴다.

**현재 판정**: 3단계 착수 전에 이 선택을 확정해야 한다. `TASK-026` 이 이 자리다.
선정하지 않고 넘어가면 "fixture replay 바이트 동일" 이 깨진다.

## 7. lookaround 를 쓰는 정적 리터럴 5곳

모두 정적이라 옮길 대상이 아니지만, **이식성이 깨지는 지점을 미리 아는 것**이 목적이므로 전수를 적는다.

| 위치 | 정규식 | 종류 |
|------|--------|------|
| `src/parsers/git/diff.ts:117` | `/(?=^diff --git )/m` | 전방 탐색 |
| `src/parsers/fs/ls.ts:30` | `/^(?![bcdlps-][rwxsStT-]{9})(\S.*):$/` | 부정 전방 탐색 |
| `src/parsers/fs/stat.ts:123` | `/(?=^\s*File:)/m` | 전방 탐색 |
| `src/parsers/windows/tasklist.ts:55` | `/ (?=[^ ])/` | 전방 탐색 |
| `src/parsers/contracts.ts:75` | `/^total \d+|^(?![bcdlps-][rwxsStT-]{9})\S.*:$/` | 부정 전방 탐색 |

`src/parsers/fs/ls.ts:27` 의 `new RegExp` 조합에도 `\\d` 가 들어가지만 이건 정적 조합이라 해당 없음.

## 8. 역방향 참조

`\1` 부터 `\9` 까지의 역방향 참조를 쓰는 곳은 **한 곳도 없다.** 검색 근거:

```bash
grep -rInE '\\[1-9]' src --include='*.ts'   # 결과 없음
```

## 9. 역추적(catastrophic backtracking) 위험

정적 리터럴 가운데 역추적이 걸릴 수 있는 형태(중첩 수량자, 겹치는 대안)는 조사 결과 없다.
`src/parsers/fs/ls.ts:27` 의 `(\d+(?:,\s*\d+)?)` 같은 형태는 수량자 중첩이 없고
선택 분기가 하나뿐이라 위험하지 않다.

**중요한 정정**: Rust `regex` 를 쓰는 이유는 "parism 이 지금 역추적으로 죽는다"가 아니다.
지금 죽는 곳이 없다. Rust 가 주는 것은 **임의의 사용자 제공 패턴에 대해 선형 시간 보장이 생긴다**는
보장이다. V8 의 Irregexp 는 역추적 엔진이라 일부 패턴에서 최악 시간이 폭발할 수 있다.
사용자 설정에 `output_patterns` 를 자유롭게 적을 수 있으므로 이 보장은 실용 가치가 있다.

## 10. 3단계 진입 게이트 판정

| 조건 | 결과 |
|------|------|
| 옮길 대상에 lookaround 가 있는가 | 없음 (5절) |
| 옮길 대상에 역방향 참조가 있는가 | 없음 (8절) |
| 옮길 대상에 유니코드 의미 차이가 있는가 | **있음** (6절, `\b` 2건) |
| 게이트 통과 조건 | lookaround·역참조 부재 → 통과. 유니코드 차이는 `TASK-026` 으로 따로 확정 |

**결론**: 3단계에 들어가도 된다. 다만 착수 전에 `\b` 처리 방식을 확정해야 하며,
확정하지 않은 상태로 이식하면 `REQ-009` 가 깨진다.
