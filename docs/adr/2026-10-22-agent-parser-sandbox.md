> **What:** vm.runInContext의 require 제한, 허용 모듈 화이트리스트, child_process/native addon 차단 전략을 ADR로 문서화
> **Why:** 에이전트 생성 파서를 sandbox에서 실행할 때 보안 정책이 없으면 임의 코드 실행 위험. Phase 2 구현 전 설계 결정 필요.

여기서 한 가지 사실을 먼저 분명히 해야 한다. **Node.js 공식 문서는 `node:vm` 이 보안 메커니즘이 아니라고 못한다.**

> "The node:vm module is not a security mechanism. Do not use it to run untrusted code."

같은 힙과 이벤트 루프를 공유하고, `this.constructor.constructor` 을 통한 탈출이 알려져 있으며, `timeout` 은 동기 실행에만 적용되어 끝나지 않는 비동기 코드를 막지 못한다.

그러니 "vm + require 화이트리스트" 는 **보안 경계가 아니다.** 이 ADR 은 그 사실을 그대로 기록한다 — 요구사항이 그랬으므로. 그리고 **화이트리스트가 실제로 무엇을 막는지**를 정밀하게 밝힌다.

## 결정

### 1. `node:vm` 은 사용하지 않는다

에이전트 생성 파서를 `vm.runInContext` 에 넣지 않는다. 그 이유는 단순하다 — **막지 못하는 것을 막은 것처럼 보이게 하기 때문**이다. `require` 화이트리스트를 통과한 코드가 `process` 를 만지면 `child_process` 로 프로그램을 실행하고, `fs` 로 파일을 읽고 쓰고, `net` 으로 네트워크에 접속할 수 있다. 그 뒤 남는 것은 화이트리스트 한 겹뿐이며, 그 겹도 `constructor` 체인으로 우회 가능하다.

기존 외부 팩 ADR 이 `node:vm` 을 기각한 이유와 같다. **같은 결론을 두 번 도출하는 것이 아니라, 같은 근거를 두 위협 모델에 적용하는 것이다.**

### 2. 진짜 경계는 **프로세스 분리 + OS 권한 제한**이다

에이전트 생성 파서는 `child_process.fork` 로 **별도 프로세스**에서 실행한다. 워커가 아니라 프로세스다 — 프로세스는 새 권한 모델, 새 파일 기술자, 새 메모리 공간을 갖는다.

| 계층 | 보장하는 것 | 보장하지 **않는** 것 |
|------|-----------|-------------------|
| **1. 프로세스 분리** (fork) | 크래시·무한루프·메모리 폭발이 서버를 죽이지 않는다 | 서버와 **같은 사용자 권한**으로 실행된다 |
| **2. Node.js 권한 모델** (`--permission`) | 파일 시스템·자식 프로세스·환경 변수 접근을 **허용 목록으로 제한** | `--allow-fs-read` 로 허용한 경로 밖은 못 읽는다 — **이게 실질 경계** |
| **3. 네트워크 차단** (선택) | `--experimental-permission` + 방화벽/네트워크 네임스페이스 | 컨테이너를 쓰지 않으면 전역 설정이 필요하다 |
| **4. CPU·메모리 상한** | `ulimit`/cgroup 또는 `timeout` + `resourceLimits` | — |

**2번이 실질적인 경계**다. `--permission` 플래그가 붙은 자식 프로세스는 명시적으로 허용한 파일 읽기·쓰기 경로와 자식 프로세스 실행 외에는 아무것도 못 한다. 이것은 OS가 강제하는 것이므로 JS 코드로는 우회할 수 없다.

### 3. 동기 parse 계약은 "동기 API를 유지하되, 기다림은 부모가 책임진다"로 해결한다

레지스트리의 `parse()` 는 동기 API이고 엔진·CLI·라이브러리 소비자가 그 계약에 의존한다. 이 계약은 **바꾸지 않는다.**

외부 팩 ADR 과 달리, 에이전트 생성 파서의 기다림은 **동기 대기가 필요 없다.** 에이전트 생성 파서는 요청마다 새로 만들어지는 **일회성**이다 — 상주하지 않는다. 그러므로:

- 파서 생성·실행·결과 수신은 **비동기**로 끝낸다.
- 결과를 **동기 API로 돌려야 하는 자리**(레지스트리 `parse()`)에서만 동기 대기를 건다.
- 이 대기는 **부모 프로세스가 자식의 종료/응답을 기다리는 것**이며, 타임아웃이 반드시 있다.

자식 프로세스를 **상주 서버로 띄워 두지 않는다** — 상주하면 그 프로세스 하나가 평생 권한을 갖는다. 일회성이 권한의 수명을 요청 길이로 제한한다.

### 4. 구체적인 차단 목록

자식 프로세스에 아래를 적용한다.

**Node.js 권한 모델로 차단**
- `child_process` 실행 전체 (허용할 명령이 있으면 `--allow-child-process` 로 명시)
- 파일 읽기: **허용 경로만** (`--allow-fs-read=<경로>`). 허용 경로는 가드의 `allowed_paths` 와 같은 규칙(실경로 기준)으로 산출한다.
- 파일 쓰기: **기본 차단**. 허용 경로를 명시적으로 `--allow-fs-write` 으로 열어야 하며, **기본값은 쓰기 금지**다.
- 환경 변수: `--allow-env` 로 명시한 것 외에 읽지 못한다. **토큰·키를 환경 변수로 넘기지 않는다.**
- 네이티브 애드온: `--allow-addon` 없이는 로드할 수 없다. **기본 차단.**

**코드 수준에서 차단**
- `worker_threads` 재사용 금지(중첩 격리는 복잡도만 올리고 경계는 안 세진다)
- 자식이 넘긴 결과는 **구조화 복제 가능 값만** 받는다. 함수·Promise·Symbol 은 실패로 처리한다(외부 팩과 동일한 계약).
- 결과 크기 상한: 자식이 무한히 큰 문자열을 보내지 못하게 **메시지 크기 상한**을 건다.

**상한**
- 시간: 호출당 제한. 외부 팩의 500ms 보다 **엄격하게** 잡는다 — 에이전트 생성 파서는 신뢰도가 낮으므로.
- 메모리: `resourceLimits` 는 V8 old generation 만 제한한다(`Buffer`·`ArrayBuffer` 는 제한 안 됨). 그래서 **메시지 크기 상한을 함께 둔다** — 실제 폭발의 주 경로가 그쪽이다.

### 5. 실패는 조용히 삼키지 않는다

- 격리를 **끄는** 설정은 제공하지 않는다. Phase 2 파서는 격리가 기본이다. `parsers.external_isolation: "none"` 처럼 격리를 끄는 escape hatch는 **없다** — 외부 팩에는 있는 예외다.
- 상한 초과·비정상 종료·권한 거부·크기 초과 는 각각 **다른 reason**으로 보고한다. 원인이 다르면 무엇을 해야 하는지도 다르다.
- 격리 경로가 아예 준비되지 않았으면 파서를 **거절**한다. 서버 프로세스에서 그냥 실행하지 않는다.

### 6. 사용자에게 무엇을 보장하는지 명확히 밝힌다

문서(README·SECURITY.md)에 다음을 **명시**한다.

> Phase 2의 에이전트 생성 파서는 별도 프로세스에서 Node.js 권한 모델로 실행된다. 파일 시스템 접근은 허용 경로로 제한되고, 자식 프로세스 실행·네트워크 접속·환경 변수 접근은 기본적으로 차단된다. **그렇지만 이것은 운영 환경의 사용자 권한 안에서 동작한다** — 커널 샌드박스(seccomp·AppArmor)와는 다르다. 더 강한 격리가 필요하면 컨테이너 안에서 parism 을 실행하라.

### 7. 대안으로 Wasmtime capability 샌드박스를 추가한다 (Phase 4, 2026-10-22 개정)

`node:vm` 기각 사유는 **그대로 유지한다.** 그 판단이 틀렸다는 근거가 없다.

그런데 Phase 4 는 다른 질문에 부딪힌다. **외부 ParserPack** 은 사람이 가져온 코드지만
**신뢰할 수 없는 코드**일 수 있다. 워커는 결함 격리는 하지만 보안 경계가 아니다.

그래서 **Wasmtime capability 샌드박스** 를 대안으로 추가한다.

| | 워커 격리 (기존) | Wasmtime capability 샌드박스 (Phase 4) |
|---|---|---|
| 성격 | 결함 격리 | **보안 경계** |
| 파일 접근 | 워커의 권한 그대로 | **열어 준 경로만** |
| 네트워크 | 워커의 권한 그대로 | **없음** |
| 환경 변수 | 워커의 권한 그대로 | **열어 준 것만** |
| 메모리 | V8 old generation 만 제한 | 게스트 **선형 메모리** 전체 |
| 시간 | 워커 임계값 | **Wasmtime epoch 타임아웃** |

#### 무엇을 보장하는가

1. **메모리** — 10MiB 를 넘으면 트랩한다.
2. **실행 시간** — epoch 타임아웃(기본 60초) 이 지나면 멈춘다.
3. **연료** — 무한루프가 연료를 다 쓰면 멈춘다.
4. **접근 권한** — capability 맵이 비어 있으면 파일·환경 변수·네트워크를 **전부 거부한다.**
5. **격리** — 호출마다 새 `Store`·`Linker`·인스턴스. **호출 사이에 공유 상태가 없다.**
6. **시크릿** — 게스트는 존재 여부만 받는다. **값은 주지 않는다.**

#### 무엇을 보장하지 **않는**가 — 이 절이 없으면 결정이 방어선보다 커 보인다

> **이것은 OS 샌드박스가 아니다. 경계가 아니다.**
> 커널 격리(seccomp·AppArmor·네트워크 네임스페이스)가 아니다. parism 과 **같은 사용자 권한**으로 돈다.
>
> **그리고 메모리 안전 언어의 한계가 그대로 남는다.**
> 게스트 안의 **로직 취약점**은 샌드박스가 막지 못한다.
> 게스트가 `secret-exists` 로 값이 아니라 존재 여부만 받는 것은 그 증거다 —
> 값이 새지 않는 것은 **호스트의 결심**이지 샌드박스의 힘이 아니다.
> 게스트가 스스로 다른 경로로 값을 알아낼 수 있다면, 샌드박스는 그것을 막지 않는다.

#### 대안으로 추가한 이유와 남은 것

- **왜 추가했는가**: 워커는 결함 격리이지 보안 경계가 아니다. 외부 팩이 **신뢰할 수 없는 코드**일 수 있으므로 경계가 필요했다.
- **왜 `node:vm` 이 아니다**: Node.js 공식 문서가 보안 메커니즘이 아니라고 못한다. **같은 판단을 두 위협 모델에 적용한 것**이다.
- **왜 프로세스 분리 + `--permission` 이 아니다**: 외부 팩은 **상주**한다. 상주 프로세스 하나가 평생 권한을 갖는 구조가 되기 때문이다. Wasmtime 샌드박스는 **호스트 권한 없이** capability 안에서만 돈다.
- **남은 것**: 외부 팩 형식의 완전한 교체(워커 경로 제거)와 `parism init-parser` 스캐폴드 변경은 **미완**이다.
  현재는 `parser.wasm` 이 있는 팩이 샌드박스 경로를 타고, `parser.js` 팩은 기존 워커 경로를 탄다.
  **워커 경로는 보안 경계가 아니다** — 이 사실은 공개 문서에 적혀야 한다.

## 이 결정이 주는 것과 주지 않는 것

**주는 것**: 에이전트 생성 파서가 서버 프로세스와 같은 권한을 갖지 않는다. `--permission` 으로 강제되는 경계는 JS 코드로는 우회할 수 없다. 권한의 수명이 요청 길이로 제한된다(일회성 프로세스).

**주지 않는 것**:
- **커널 격리가 아니다.** 같은 사용자 권한 안에서 돌아간다. 같은 사용자가 읽을 수 있는 파일은 파서도 읽을 수 있다(허용 경로가 아니라면 OS 권한으로는 막히지 않는다).
- **메모리 안전 언어의 한계가 남는다.** 샌드박스는 메모리 안전을 보장할 뿐 **로직 취약점은 보장하지 않는다.**
- **워커 경로는 보안 경계가 아니다.** Wasmtime 샌드박스 경로만 경계다.
- **네트워크는 설정 의존이다.** 컨테이너를 쓰지 않으면 자식이 네트워크에 나갈 수 있다. 네트워크를 확실히 막으려면 컨테이너/네임스페이스가 필요하다.
- **CPU 시간 상한은 강제되지 않을 수 있다.** `timeout` 은 프로세스를 **죽이지 않으면** CPU를 계속 쓴다. 확실한 CPU 제한은 cgroup/`ulimit` 이다.
- **같은 사용자 안에서의 정보 노출은 막지 않는다.** 허용 경로 밖의 파일을 못 읽게 하는 것이지, 이미 읽을 수 있는 정보를 못 보게 하는 것이 아니다.

## 대안

- **`node:vm` + require 화이트리스트 (기각)**: Node.js 공식 문서가 보안 메커니즘이 아니라고 명시한다. `constructor` 체인 탈출이 알려져 있고, 비동기 무한루프를 `timeout` 이 못 막는다. **require 화이트리스트는 심층 방어 한 겹으로만 쓸 수 있다.**
- **워커 격리 재사용 (기각)**: 워커는 같은 프로세스의 권한을 그대로 갖는다. 에이전트 생성 코드에는 그 권한이 너무 많다. 결함 격리에는 충분하지만 임의 코드 실행을 막지 못한다.
- **`child_process.fork` + 권한 모델 없음 (기각)**: 프로세스는 분리하지만 권한은 같다. 파일 읽기·쓰기·네트워크·자식 실행이 모두 가능하다. 경계가 없다.
- **컨테이너가 유일한 해법 (채택하지 않되 권장)**: 가장 강한 경계다. 그러나 parism 은 "Node.js 라이브러리로도 쓸 수 있다"를 목표로 한다 — 컨테이너를 요구하면 라이브러리 사용성을 잃는다. **추천**한다: 프로덕션에서 에이전트 생성 파서를 쓸 계획이면 parism 을 컨테이너 안에서 실행하라.
- **신뢰하지 않는 파서를 아예 받지 않기 (병행)**: 사용자가 자신의 파서를 직접 설치하는 경로(외부 팩)를 유지한다. 이미 워커 격리로 결함은 격리된다.

## 결과

- Phase 2 착수 전 선결 조건(TODOS.md)이 충족된다.
- 에이전트 생성 파서의 격리 수준은 **외부 팩보다 엄격**하다 — 신뢰도가 낮으므로.
- 기본값이 안전하다. 격리를 끄는 설정이 없고, 격리가 없으면 거절한다.
- 라이브러리 모드(`@nerdvana/parism/engine`)에서도 같은 격리가 적용된다 — Phase 2 파서는 **생성된 뒤 서버 안에서** 실행되므로, 어느 배포 면이든 경계가 같아야 한다.
- **추후**: 컨테이너 실행 가이드와, 컨테이너 안에서 `--permission` 을 생략해도 되는 구성을 문서로 제공할 것을 검토한다.

### Phase 4 Wasmtime capability 샌드박스의 실측 (2026-10-22)

| 측정 | 값 |
|------|-----|

**발견한 결함**: 시험용 게스트의 "무한 루프" 가 **최적화로 접혀 1.2ms 만에 끝났다**(실측).
LLVM 이 반복 횟수 2^64 를 상수로 계산해 루프 전체를 한 줄로 접은 것이다.
`black_box` 으로 최적화기에 "이 값은 모른다" 고 말해 막았다.
**무한 루프가 아니라면 무한 루프를 못 잡는 것과 같다.**
