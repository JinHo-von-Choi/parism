# ADR: 환경 인식 계층 — "명령이 없다" 를 다음 행동으로 바꾼다

- **작성자**: 최진호
- **작성일**: 2026-10-22
- **수정일**: 2026-10-22
- **상태**: 채택, 구현 완료 (v2.2.0)

## 맥락

parism 은 허용 목록에 있는 명령을 실행한다. 그 명령이 **이 호스트에 없으면** 지금은 이렇게 된다.

```json
{ "kind": "exec", "reason": "spawn_failed", "message": "spawn helm ENOENT" }
```

`spawn helm ENOENT` 에서 에이전트가 뽑아낼 수 있는 것은 "실패했다" 뿐이다. 무엇을 해야 하는지는 나오지 않는다. 에이전트는 그대로 같은 명령을 다시 시도하거나, 사용자에게 실패를 알리고 멈춘다.

Terminal-Bench 2.0 의 실패 분류에서 **"PATH 에 없는 실행파일 호출" 이 전체 명령 실패의 24.1%** 로 가장 큰 실패 모드였다. 같은 논문은 해법으로 "첫 관측에 도구 인벤토리를 주입" 하고 "command_not_found 처리 훅" 을 거는 것을 처방한다. 즉 이 문제는 parism 이 특히 잘할 수 있는 자리다. parism 은 이미 **가드를 통과한 명령만** 실행하므로, 그 명령을 못 쓸 때는 두 가지 중 하나일 뿐이다 — **설치돼 있지 않다**거나 **설치돼 있지만 실행 권한이 없다.**

이 계층이 없으면 parism 은 "명령이 없는 환경" 에서 에이전트를 가장 많이 좌절시키는 도구가 된다. 그리고 그 좌절을 parism 자신의 책임으로 돌리지 않는다. 그리고 그 사실을 사용자에게 알리지도 않는다.

## 결정

### 1. 실행하지 않고 조회만 한다

설치 상태는 `fs.accessSync(path, X_OK)` 로 판정한다. **실행하지 않는다.** 명령을 직접 실행해 "되나?" 하고 확인하는 것은 부작용이 있다.

판정 결과는 세 가지다.

| 상태 | 뜻 | 다음 행동 |
|------|-----|----------|
| `installed` | 이 호스트에서 실행할 수 있다 | 없음 |
| `missing` | PATH 어디에도 없다 | 설치 지시 + 대체 명령 |
| `not_executable` | **있다가** 실행 권한이 없다 | 설치해도 소용없다 |

`missing` 과 `not_executable` 를 나누는 이유는 **원인이 다르기** 때문이다. `not_executable` 은 설치를 권하지 않는다 — 설치해도 실행 권한은 그대로다.

PATH 해석은 셸의 규칙을 따른다. 빈 PATH 항목은 현재 디렉터리로 해석하고, 실행 권한이 없는 파일을 만나면 **다음 항목으로 간다**(execvp 규칙). 심볼릭 링크는 `realpathSync` 로 대상을 확정한다.

### 2. 설치 지시는 정적 테이블에서만 만든다

**명령 이름에서 패키지 이름을 추측하지 않는다.** `helm` 의 패키지가 `helm` 이라고 가정하면 `kubectl` 에서도 존재하지 않는 이름을 말하게 된다.

`src/engine/install-hints.ts` 의 표가 유일한 출처다. 표에 없는 명령은 `install` 없이 `status` 만 돌려준다. 없는 정보를 지어내면 그건 안내가 아니라 오답이다.

**패키지 이름은 관리자마다 다를 수 있다.** `kubectl` 의 apt 패키지명은 `kubernetes-client` 이고 dnf 에서는 `kubectl` 다. 그래서 패키지 이름은 관리자별로 적는다. 도구 이름 하나를 모든 관리자에 그대로 적용하면 안 되는 이유가 이것이다.

**자기 자신으로 설치되는 항목은 넣지 않는다.** `apt` 와 `brew` 는 자기 자신으로 설치되지 않는다. 그런 항목을 넣으면 안내를 읽는 쪽이 곧바로 실패한다.

**없는 방법은 없다고 적는다.** `helm` 은 npm 패키지로 설치되지 않는다(npm 의 `helm` 패키지는 버전 0.2.1 의 무관한 도구다). 공식 설치 스크립트는 셸 파이프라인이라 안내하지 않는다. 없는 방법을 지어내지 않으려면 항목이 비어 있어야 한다.

### 3. 관리자는 "이 호스트에 있는 것" 으로 고른다

리눅스는 배포판마다 관리자가 다르다. `/etc/os-release` 을 읽지 않는다 — 읽을 이유가 없고, 허용 경로 밖 읽기는 경계를 흐린다. 대신 **그 관리자 바이너리가 이 호스트에 있는지 조회해서** 첫 번째 사용 가능한 것을 고른다.

없는 관리자를 안내하면 에이전트가 곧바로 실패하는 한 번 더를 만나게 된다.

### 4. 대체 명령은 가드 allowlist 안에서만 고른다

`netstat` 이 없으면 `ss` 로, `helm` 이 없으면 `kubectl` 로. 대체는 **같은 일을 하는** 명령이어야 하고, **현재 가드 allowlist 안에 있어야 한다.** allowlist 밖의 명령을 안내하면 그 지시가 곧바로 막힌다.

대체 목록은 포맷 힌트(`describeCommand().alternatives`)와 **다른 개념**이라 필드명도 분리했다. 같은 이름으로 두 가지를 섞으면 어느 쪽을 읽는지 알 수 없다.

### 5. 기존 `failure.kind` 와 `failure.reason` 은 바꾸지 않는다

`kind` 의 값 집합과 `reason` 의 기존 문자열 값은 그대로 둔다. 새 정보는 `failure.availability` 라는 **추가 필드**로만 들어간다.

`kind` 와 `reason` 을 바꾸면 하위 호환이 깨진다. 그리고 "명령이 없다" 는 **실패의 종류**가 아니라 **실패의 해석**이다. 종류와 해석을 같은 자리에 넣지 않는다.

`errorCode` 도 추가했다. `spawn helm ENOENT` 라는 **메시지 문자열에서 errno 코드를 다시 꺼내는 대신** 구조적으로 읽게 하기 위해서다.

### 6. `describe()` 로도 설치 상태를 미리 본다

에이전트는 실행하기 전에 무엇을 쓸 수 있는지 알고 싶어 한다. `describe()` 응답에 `command_availability` (허용 명령 전체의 설치 상태 맵) 를 넣고, `describe(cmd)` 응답에는 **없을 때만** `availability` 를 붙인다.

"설치돼 있음" 은 기본값이라 싣지 않는다. 모든 명령에 붙이면 `describe(cmd)` 의 2KB 예산을 다 쓰고, 알려줄 일 없는 정보가 된다.

## 이 결정이 주는 것과 주지 않는 것

**주는 것**: 실행이 ENOENT 로 실패하면 응답이 "무엇을 해야 하는지" 를 담는다. 설치 명령은 그 호스트에서 실제로 쓸 수 있는 관리자의 것이고, 대체 명령은 현재 가드 안의 실제 명령이다. 실패를 다음 행동으로 바꾸는 데 필요한 정보가 **추가 도구 호출 없이** 담긴다.

**주지 않는 것**:

- **이 계층은 명령을 설치하지 않는다.** 설치 지시는 문자열이다. 그 문자열을 실행하는 것은 에이전트(또는 사람)다.
- **PATH 조회에 60초 캐시가 있다.** 그 사이에 설치하면 반영되지 않는다. 캐시가 expire 되면 다시 본다.
- **`not_executable` 에는 설치 지시가 없다.** 설치로 해결되지 않는 문제에 지시를 붙이면 안내가 거짓말이 된다.
- **설치 지시의 성공을 보증하지 않는다.** 패키지 저장소가 해당 이름을 없을 수 있고, 관리자가 root 권한을 요구할 수 있다. 지시는 **시도할 이유**를 주는 것이지 성공을 예고하는 것이 아니다.
- **이 계층은 가드를 바꾸지 않는다.** 가드가 막은 명령에는 `availability` 가 붙지 않는다. "실행할 수 없는 것" 과 "설치 안 된 것" 은 다른 사실이다.

## 대안

- **실행해서 확인한다 (기각)**: `command --version` 을 직접 돌려 본다. 부작용이 있고, "실행하면 부작용이 없고" 라는 조건을 만족하지 않는다.
- **명령 이름에서 패키지 이름을 추측한다 (기각)**: `helm` → `helm`, `kubectl` → `kubectl`. 검색으로 찾아 넣을 수는 있지만, 없는 패키지 이름을 지어내기도 한다. 지시한 명령이 실패하면 그건 설치 문제가 아니라 안내를 못 믿은 문제가 된다.
- **`/etc/os-release` 로 배포판을 읽는다 (기각)**: 배포판을 정확히 알면 좋지만, 허용 경로 밖의 파일을 읽는 것은 이 프로젝트의 경계와 맞지 않는다. 관리자 바이너리 존재 여부로 충분하다.
- **`describe()` 실패에 설치 지시를 항상 싣는다 (기각)**: `describe(cmd)` 의 2KB 예산을 넘긴다(실측 2055 > 2048). 알고리즘이 아니라 계약 위반이다.
- **설치 지시를 `message` 문자열에 이어붙인다 (기각)**: 문자열은 구조가 아니다. 파싱해야 한다. 필드로 분리한다.
- **실패를 `kind: "guard"` 로 바꾼다 (기각)**: "명령이 없다" 는 가드가 막은 게 아니다. `kind` 를 바꾸면 가드 차이와 실행 실패가 뒤섞인다.
- **대체 명령을 포맷 힌트와 같은 필드에 넣는다 (기각)**: 두 개념이 섞인다. 필드명을 분리한다.

## 결과

- `src/engine/availability.ts` — PATH 조회(60초 캐시), 대체 명령 표, 실패 정보 조립.
- `src/engine/install-hints.ts` — 정적 설치 표. 패키지 이름은 `apt-cache` 와 npm 레지스트리로 검증했다.
- `FailureInfo.availability` 과 `FailureInfo.errorCode` 가 새로 생겼다. 기존 `kind`/`reason` 은 그대로다.
- `DescribeResult.command_availability` 로 허용 명령 전체의 설치 상태를 미리 볼 수 있다.
- MCP 도구 설명에 설치 지시와 대체 명령의 쓰법을 적어, 에이전트가 같은 명령을 되풀이하지 않게 했다.
