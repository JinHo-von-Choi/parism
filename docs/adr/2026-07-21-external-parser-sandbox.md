# ADR: 외부 ParserPack 실행 격리 전략

- **작성자**: 최진호
- **작성일**: 2026-07-21
- **상태**: 제안 (Phase 2 구현 전 선결 조건)

## 맥락

`~/.parism/parsers/`에 등록된 외부 ParserPack은 `parism add`로 영구 등록된 뒤, MCP 서버 시작 시 현재 Node.js 프로세스 컨텍스트에서 직접 `import`되어 로드된다(`src/cli/auto-loader.ts`). 이 로드 경로는 프로세스 격리, `vm` 기반 컨텍스트 분리, 모듈 접근 제한 중 어느 것도 적용하지 않는다.

외부 ParserPack의 `parse()` 함수는 임의의 Node.js 모듈(`child_process`, `fs`, 네이티브 애드온 포함)에 제약 없이 접근할 수 있다. 파서가 로컬에서 사용자 본인이 작성한 것이라면 위험 반경이 제한적이나, Phase 2에서 계획된 원격/공유 파서 배포 또는 다중 사용자 환경으로 확장될 경우 신뢰할 수 없는 코드가 동일 프로세스 권한으로 실행되는 구조가 된다.

## 결정

Phase 2(원격/공유 ParserPack 실행)에 착수하기 전, 다음 세 가지를 설계·문서화한다.

1. **`vm.runInContext` 기반 격리 컨텍스트**: 외부 ParserPack의 `parse()` 실행을 별도 `vm.Context`에서 수행한다. 기본 Node.js `vm` 모듈은 `require`를 컨텍스트 내부에서 차단하지 않으므로, 컨텍스트에 주입하는 전역 객체에서 `require`/`process.binding`/`process.mainModule` 등 상위 프로세스 접근 경로를 제거한다.
2. **허용 모듈 화이트리스트**: ParserPack이 사용할 수 있는 모듈을 순수 파싱에 필요한 범위(예: 정규식·문자열 유틸리티에 국한된 내부 헬퍼)로 한정하는 화이트리스트 `require` 셔틀을 컨텍스트에 주입한다. 화이트리스트 밖 모듈 요청은 예외로 거부한다.
3. **`child_process`/네이티브 애드온 차단**: 컨텍스트에서 `child_process`, `worker_threads`, `.node` 네이티브 바인딩으로 이어지는 모든 경로를 화이트리스트에서 원천 제외한다. 파서는 `raw` 문자열 입력을 받아 구조화된 값을 반환하는 순수 함수 계약을 유지하며, 그 외 I/O나 프로세스 생성 권한을 가지지 않는다.

## 대안

- **프로세스 분리(`child_process.fork` + IPC)**: 완전한 메모리 격리를 제공하나, 파서 호출당 프로세스 기동 비용이 추가되어 `describe → dry_run → run` 온보딩 루프의 지연을 늘린다. `vm` 기반 격리 대비 구현·운영 복잡도가 높다.
- **정적 분석만으로 사후 검증**: ParserPack 코드를 로드 전 AST 스캔하여 위험 API 호출을 탐지하는 방식. 동적 `eval`/문자열 조합 호출 등 정적 분석을 우회하는 패턴에 취약하여 단독 방어로는 불충분하다.
- **현행 유지(격리 없음)**: 단일 사용자·로컬 신뢰 환경에서는 즉시 위험이 낮으나, Phase 2의 원격/공유 배포 전제와 충돌한다. Phase 2 착수 전 최소한 설계 결정을 문서화해 두어야 구현 시점에 재작업을 피할 수 있다.

## 결과

- `vm.runInContext` 격리, 모듈 화이트리스트, `child_process`/네이티브 애드온 차단 세 가지를 Phase 2 구현의 선결 설계로 확정한다.
- 격리 컨텍스트로 인한 성능 오버헤드는 `benchmarks/`에 파서 실행 시나리오를 추가하여 Phase 2 구현과 함께 측정한다.
- 화이트리스트 모듈 목록과 컨텍스트 전역 객체 구성의 세부 사양은 Phase 2 구현 착수 시 별도 설계 문서로 확정한다.
